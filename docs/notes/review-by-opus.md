# レビューを Fable から Opus xhigh に替えるときの懸念と、うまくいかせる決まり

2026-09-25、持ち主の問い「いまは Opus medium が実装して Fable high がレビューしているが、節約のために Opus medium + Opus xhigh にしたい。何が懸念で、どうすればうまくいくか」への Fable の検討。根拠はこの日までの実例（TODO.md の T72・T77・T82・T93・T96・T98〜T100・T109・T110）。

## 結論

**できる。ただし「読むだけのレビュー」にしないこと。** この 1 日の実例で、レビューが実際に捕まえたものの大半は「読んで気づいた」のではなく「走らせて・境界値を入れて・CI の記録を読んで」見つかっている。同じモデルが実装と審査の両方をすると、読むだけのレビューは実装と同じ思い込みを共有して素通しになる。だから決まりは 3 つ:

1. **レビューは別の会話で、実装の文脈を持たずに始める**（同じ会話の続きで「自分の書いたものを見直す」形にしない）。
2. **OK と言う前に必ず動かす**（pytest・smoke・forward-check に加えて、ページや Worker を触る変更は **CI の実ブラウザで本番相当を 1 回**）。
3. **設計の判定は「数字と式と、判定を覆す条件」を書く**（読めば持ち主が追える形にする）。

Fable は残す。ただし呼ぶのは下の「Fable に回すもの」だけにする。

## 懸念（実例つき）

### 1. 同じモデルは同じ思い込みを共有する

- T72（2026-09-21）: 変換器が `rotary` と `parallel_residual` をエンジンに渡していなかった。**テストは全部通り、ブラウザで「動くが文章が壊れる」形で出た。** テストが `Llama()` を直接呼んでいたので、実装した側の前提（設定はちゃんと渡る）を試験も共有していた。
- T77・T85: `layout()` と engine に `bias` / `arch` を足したのに `checkpoint_dtype()` と `convert_hf.py` に足し忘れた。**「`arch` を受け取る関数を足したら呼び出し側を全部探す」**という機械的な確認で捕まる種類だが、実装した側は「足した」と思っているので探さない。
- 今日の T109（Fable 自身の変更）: helper.js の先頭に本当に待つ `await import()` を置いたら、ブラウザは最初のメッセージを取りこぼしてページが止まった。**Node の試験は全部通った**（Node はメッセージを溜める）。捕まえたのは CI の画面撮りと本番確認で、レビューではない。Fable でも同じ思い込み（Node で通れば動く）を持った。

**同じモデルにすると、この種の素通しが増える**と見るのが妥当。対策は「別の会話」「動かす」「機械的な確認の一覧」で、モデルの賢さで埋めない。

### 2. 設計の判定は「読み方」に価値がある

今日の判定で、Fable が足したものは次の 3 つ。Opus xhigh にもできるはずだが、**「書き方を決めておく」ことで質を保つ**。

- T98: Opus の表は「llama.cpp の Q4_K_M は +3〜5%」で止まっていた。Fable はそれが名前に反して**大半 5 ビット + 一部 6 ビット**（dim が 256 の倍数でないため）だと読み、「4 ビットは届かない、5 ビットの一様な形式なら届く見込み」に変えた。表の数字ではなく、数字がどの条件から出たかを読んだ。
- T100: Opus は受け入れ率と費用を測って報告した。Fable はそれを 1 つの式（1 回で進むトークン数 ÷（確かめる費用 + 下書きの費用））に入れ、いちばん有望な組でも 0.95 倍と出して「実装しない」と判定した。**測ることと、測った数字で決めることは別の仕事**。
- T101: `asc` の CLI が 32 ビット固定でも、コンパイラの公開 API で `Target.Wasm64` を選べることを読んで、C への書き直しでなく「小さなドライバ」の道を書いた。

**判定の書式を決める**: (a) 使う数字と出どころ、(b) 式、(c) 判定、(d) **判定を覆す条件**（「これが測れて X 以上なら逆」）。(d) があると、持ち主が判定を追えるし、次の回で見直せる。

### 3. 「見た目」と「訪問者に見える文」の判断

描画のタスク（T75・T76・T88）を Fable に寄せていたのは、見た目の判断のため。今日、**CI で画面を撮って持ち主が見る仕組み**（`preview.yml`・`tests/screenshots.mjs`）ができたので、これは Opus でよい。決まりはそのまま: コミットの前にスマホ幅と PC 幅の画面を撮って持ち主に見せる、訪問者に見える日本語は先に文面を出す。

### 4. レビュー担当が「OK」を出しやすくなる

同じモデルの xhigh は、実装した側の説明（TODO.md の記録）を読んで納得しやすい。今日のレビューで must-fix が出たのは 6 件中 3 件（T74・T82・T99）で、どれも**記録に書かれていないところ**（境界、失敗の経路、戻り値）を突いて出た。「記録を読んで確かめる」のではなく「記録に無いところを探す」のが役目。

## うまくいかせる決まり

### レビューの手順（OK と言う前に全部やる）

1. **別の会話で始める。** 入力は TODO.md の項と `git diff`、AGENTS.md。実装した会話の文脈は持ち込まない。並列にするならサブエージェントを**新規**で（fork でなく）起こし、同じ入力だけを渡す。
2. **動かす。** `.venv/bin/python -m pytest tests -q`（リポジトリの中の venv、docs/notes/dev-setup.md。system の python3 では 62 件が skip になる）、`node tests/smoke.mjs`、`node tests/forward-check.mjs`（共有と `--plain` の両方）、スレッドに触るなら `node tests/threads-check.mjs`。**ページか Worker か forward.js か helper.js に触る変更は、`models.yml` を本番に対して走らせて通るまで OK と言わない**（今日の T109 の止まりは、これだけが捕まえた）。
3. **境界を自分で入れる。** レビュー担当は「記録にある確認」を信じず、記録に無い入力を 1 つ以上足す（今日の例: `to_f16` の 326 個の境界値、`attention_f16` の half の全数、GPT-2 の外れ値の列 × 下書き）。リポジトリに入れるかは別として、やったことを記録に書く。
4. **機械的な確認の一覧を回す**（AGENTS.md の落とし穴から）: `arch` / `bias` / `dtype` を受け取る関数を足したら呼び出し側を全部探す、legacy 形式を変えたら 3 か所 + Cache の鍵、Worker が読むファイルを足したら `?v=`、モジュール Worker の先頭で await しない、`git diff --cached --stat`、AGENTS.md と TODO.md が実装と合っているか。
5. **失敗の経路を読む。** 成功の経路は実装した側が確かめている。容量切れ・短い書き込み・中止・2 回目の読み込み・別のブラウザ、を 1 つずつ問う。
6. **書く**: 「レビュー（Opus xhigh、日付）: 判定。直したもの。確かめて問題なしだったもの。あれば良い（やらない）」の 1 行。must-fix が 0 の回が続いたら、それ自体を持ち主に言う（見つけられていない可能性のほうが高い）。

### 判定の手順（設計を決めるとき）

- 上の書式 (a)〜(d) で書く。数字は測ったものだけ（推測は「未計測」）。
- 選択肢が 2 つ以上あって、どちらも筋が通るときは、**選ばずに持ち主に出す**（今日の T98 の「+3〜5% を許すか」は持ち主が決めた）。
- **方針（AGENTS.md の番号つきの方針）に触る判定は持ち主**。これは今までどおり。

### Fable に回すもの（短い一覧）

- 実装とレビューの意見が割れたとき。
- 形式を変える設計（legacy 形式、Cache の鍵、Worker とページの契約）で、後から直しにくいもの。
- レビューが 3 回続けて must-fix を出さなかったとき（1 回だけ Fable に読ませて、見落としが無いか確かめる）。
- 持ち主が「数字の読み方を確かめたい」と思ったとき（T84・T95 の公開する表）。
- **GPU のシェーダ**（速さの核。T146 から、2026-09-26 の持ち主の判断。effort は max）。`.claude/agents/shader-reviewer.md` で起こす。**シェーダのほかは今までどおり Opus xhigh**（持ち主「普段のレビューは Opus xhigh でいい」）: タイルの形、共有メモリ、packed int8 の量子化、端の扱い、端末ごとの違い。

### 費用について

xhigh はトークンあたりの費用が高いが、レビューと判定の会話は短い（今日の 6 件のレビューはサブエージェント 3 本で合計 30 分弱）。費用の大半は実装の会話で、そこは medium のまま。**節約になるのは「Fable を常駐させない」こと**で、レビューを薄くすることではない。上の手順 2 の CI の走行は無料ではないが、今日の T109 の止まり（本番を約 40 分止めた）を防ぐ費用としては安い。

## T226 の回（2026-10-01、Sonnet max）で分かったこと

- **must-fix は 0 件、should は 2 件（試験の目盛りと文書）で、どちらも読んだだけでは出ず、壊して動かして出た**: 層の番号の誤りを 4 通り捨てのブランチで入れて Dawn と SwiftShader で回す、偽の device で `tokenPass` の全部の形を動かす、本番のページで GPU だけの Qwen と GPT-2 を動かす、Chromium のソースで `deviceMemory` を読む。
- **1 つの線を使い回す形の試験は、線が許す距離を NumPy で先に出す**: DP4A の線（3 × Q8）は、前からの作り物では別の層の重みを読む GPU を通した（行列を 0.3 で引くので、8 ビットの丸めが層 0 から 2 で約 7 倍に伸びる）。gpu-check と同じ NumPy の答えに「層 0 の重みを全部の層で読む」誤りを入れれば、GPU を使わず数十秒で、どの形の線にどれだけ届くかが出る。線を決める前にこれを出す。
- **形ごとに別の道で読む値は、形ごとに壊し方を入れる**: RMSNorm のモデルの norm の重みは、float の形は行列の Params、DP4A の形は専用の uniform（`g.u.norm[l]`）で読む。float の形の行は後者の誤りを見ない。**コードを読んで「DP4A だけの層の添字は無い」と書いた所は、壊してみて 1 つ見つかった**（読んで「無い」と言うのは、壊して「落ちない」と言うより弱い）。
- **偽の device で計画（ディスパッチの数と、層ごとに読む重みの層）を見る試験は、1 秒で全部の族と形を見る**: `tests/gpu-token-plan-check.mjs`（ブランチ `t226-review-plan-check`、本線には入れていない）。重みの値に層の番号を埋めて 312 回の読みを、層ごとの行列とキャッシュに名札を付けて 648 個の結びを突き合わせ、わざと壊した 12 通りが全部落ちる。白箱なので、gpu.js の中の名前が変わると直す手間が要る。
