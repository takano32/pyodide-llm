## 0. 結論

**線: 「何を頼むか」は Python、「どう取るか・どこに置くか」は JavaScript。**

- Python が持つ: モデルのファイルについての知識（どのファイルが要るか、頭が何バイトか、どのトークナイザを試すか、書式はどこか、テンソルがどこにあるか）と、生成の進行（いまのまま）。
- JavaScript が持つ: ブラウザの物（fetch・取り直し・中止・Cache・OPFS・`WebAssembly.Memory`・Worker・GPU）と、それを使う判断（メモリに入るか、GPU か CPU か、何本か）、1 トークンの計算。
- **移すのは 1 つ: 変換の段取り**（`worker/convert.js` の 126 行）。Python のジェネレータが頼み、JavaScript が答える。
- **移さないのは 3 つ**: 読み込みの段取り、置き場の判断、保存した変換の台帳。どれも「Pyodide が届く前か、Pyodide の無い所で走る」が訳で、数字は §4。
- 書式の読み手を jinja2 に替えるかは持ち主の判断（§7 の 1。勧めは「替える」）。

境目をまたぐ**回数は減らない**（部品 1 つにつき 1 回は同じ）。減るのは**種類**: worker が変換器に呼ぶ名前が 11 個から 7 個になり、取り込み元の種類を足すときに触る JavaScript が 0 行になる。

## 1. いま境目を何回またいでいるか

「またぐ」は、JavaScript が Python の関数か PyProxy の方法を呼ぶ 1 回（→Py）と、Python が JavaScript の関数を呼ぶか属性を読む 1 回（→JS）。標本抽出のカーネル（ctypes で `simdkernel.so` を呼ぶ）は Pyodide の wasm の中の呼び出しで、ここでは数えない（Emscripten がその途中で JavaScript を通すかは未確認）。

### 1.1 生成（測った: `.tmp/t370/crossings-generate.mjs`、ページのエンジンを Node の Pyodide で、CPU）

forward.js のエンジンを Proxy で包み、Python が読んだ属性と呼んだ関数を全部数えた。`next()` は `worker.js` の `generate()` と同じループ。

| モデル | プロンプト | 引いた語 | →JS | 内訳 | →Py（`next()`） |
|---|---:|---:|---:|---|---:|
| tiny-lm | 5 | 33 | 68 | `forward()` 33、`tokenBlock` 33、`forwardMany()` 1、`promptBlock` 1 | 39 |
| tiny-lm | 5 | 77 | 156 | `forward()` 77、`tokenBlock` 77、`forwardMany()` 1、`promptBlock` 1 | 82 |
| stories260K | 4 | 129 | 260 | `forward()` 129、`tokenBlock` 129、`forwardMany()` 1、`promptBlock` 1 | 134 |
| llm-jp-3 150M | 4 | 129 | 260 | 同じ | 134 |

- **1 トークンに 3 回**: →JS 2 回（`forward()` と `tokenBlock` の読み）、→Py 1 回（文の片ごとの `next()`）。1 回の生成にほかに 4 回（`generate()`・`stats`・`return()`・`destroy()`）。
- プロンプトはブロック（16 トークンまで）ごとに 2 回（`forwardMany()` と `promptBlock` の読み）。
- GPU の歩（Node には GPU が無いのでコードの読み: `engine/external.py` と `engine/generation.py`）: 4 トークンごとに →JS 2 回（`tokenBlock` と `generateMany()`）、→Py は同じく片ごと。
- **気づき（T398 に採番）**: GPU が歩を取らないとき（`tokenBlock` が 0）も、`generate()` は 1 トークンごとに `engine.tokenBlock` を読む。Python から JavaScript への 1 回は 1.3〜1.7 µs（AGENTS.md の T164）で、tiny-lm の 1 トークン 1.6 ms の約 0.1%。この道具では時間は測っていない。

### 1.3 変換（測った: `.tmp/t370/crossings-convert.mjs`、本物の変換器と数える sink）

作り物の Llama（bfloat16、テンソル 56 個、85,747,680 バイト）を int8（48,258,076 バイト）に。

| 部品の大きさ | `feed()`（→Py） | `sink.write()`（→JS） | `sink.open()` | `dtype()` | 1 部品あたりの write | ファイル 1 MiB あたり |
|---|---:|---:|---:|---:|---:|---:|
| 8 MiB、カーネル | 11 | 112 | 1 | 1 | 10.2 | 1.37 |
| 16 MiB、カーネル | 6 | 106 | 1 | 1 | 17.7 | 1.30 |
| 8 MiB、NumPy | 11 | 112 | 1 | 1 | 10.2 | 1.37 |

- **部品 1 つに**: →Py 1（`feed()`）と、その中で →JS 1（部品を Python のメモリに写す `to_py()`）。
- **1 MiB 以上たまったテンソルの片 1 つに**: `sink.write()` 2 回（値とスケール）。write 1 回は →JS 1 と、JavaScript が配列を読む →Py 2（`getBuffer`・`release`）。上の 81.8 MiB で 112 × 3 + 11 × 2 = 358 回、**1 MiB に約 4.4 回**。
- **モデル 1 つに**（コードの読み、1 つの safetensors）: →Py が `kernel_quantizer()`・`kernel_readers()`・`Conversion()`（試したトークナイザの候補ごとに 1）・`finish()`・`options`（と `toJs`）・`tokenizer`・`getBuffer`・`release`・`Llama()`・`destroy()` 5 で約 15。→JS が `dtype()` 1 と `sink.open()` 1（どちらも、引数を読む →Py が 4〜6 回付く）。
- GGUF は `from_gguf()` か `gguf_weights()` を頭が足りるまで（3 回まで）、シャードは `joined_shards()` が 1。
- 時間（この機械）: `Conversion()` 22〜33 ms、feed の合計 140〜145 ms（NumPy なら 589 ms）。またぐ費用はこの中に入っている。

### 1.4 まとめ

| | 1 回あたりの単位 | 回数 |
|---|---|---:|
| 生成 | 1 トークン | 3（→JS 2、→Py 1） |
| 読み込み（サイト・保存） | 1 モデル | →Py 11〜15、→JS 6〜7。部品ごとは 0 |
| 変換 | 1 モデル | →Py 約 15、→JS 2 |
| 変換 | 1 部品（8〜16 MiB） | 2 |
| 変換 | ファイル 1 MiB | 約 4.4（write のぶん） |

速い道（1 トークン）の 3 回はもう下げ代が小さい。境目の落とし穴（PyProxy の壊し忘れ、`null` と `None`、`JsException`）が出るのは、回数の多い所ではなく**種類の多い所**: `worker/convert.js` は `.destroy()` を 8 か所、`remote` での分岐を 16 か所持つ。

**中止と失敗**（境目をまたぐ所の決まり）:
- **失敗は境目を渡さない**。「無い」（404）は答え（`None`）で、Python が次の候補に進む。ほかの失敗（回線・429・5xx・中止）は JavaScript が輪を止めて自分のエラーを投げる（T144 のレビューの決まり「404 だけが次へ進む」がそのまま 1 か所になる）。Python に JavaScript の例外を投げ入れない（`JsException` の読み替えが要らない）。
- **中止**: JavaScript が頼むのをやめ、`generator.return()` と `destroy()`。Python の `finally` が走ることは測った（§5.3）。

### 5.2 ブラウザのファイルシステムを Python のファイルとして見せる（`mountNativeFS`）→ **使わない**

### 5.3 同期の Python から Promise を待つ（JSPI、`pyodide.ffi.run_sync`）→ **使わない。ジェネレータで足りる**

Node 24 の Pyodide で 3 つの形を測った（`.tmp/t370/waiting.mjs`、頼み 2000 回）:

| 形 | 動いたか | 頼み 1 回 | 要るもの |
|---|---|---:|---|
| ジェネレータ（JavaScript が `next(答え)`） | 動く | **21 µs** | 何も（素の Python。pytest でも同じに動く） |
| コルーチン（Python が JavaScript の Promise を `await`） | 動く | 174〜180 µs | Pyodide のイベントループ。pytest では asyncio と待てる代役 |

- Pyodide の文書（stable、`pyodide.ffi.run_sync`）: 「Only works if JS Promise integration is enabled in the runtime」、入口は `runPythonAsync()`・async の Python の関数・`callPromising()` のどれか、「This feature is not yet stable」。

- **決め**: どの形でも Python が段取りを持てる。ジェネレータがいちばん速く、3 つのエンジンで同じに動き、素の Python で試験できる。JSPI は要らない。
- 中止: ジェネレータを最初の頼みの後で `return()` すると、Python の `finally` が走った（測った）。
