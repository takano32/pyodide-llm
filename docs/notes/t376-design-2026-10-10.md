## 0. The short version

The splits left the code cut at the right places, but three kinds of knowledge are still written several times and passed around as loose values:

1. **What a model's file holds** (tensor order, shapes, which layer is of which kind) — 4 Python places and 5 JavaScript places.
2. **How a matrix is stored** (dtype) — named in 37 product files outside `/benchmark/` and `shaders/`.
3. **Who owns a piece of running state** — 36 + 11 + 18 fields that any module can assign.

My recommendation is three *descriptions* that everything else reads (an architecture/layout table in Python, a dtype registry, a shader manifest), plus *ownership* for state (the module that holds a variable exports functions, never the variable). Patterns appear only where two or more implementations exist today: layouts (4), layer mixers (3), FFNs (2), norms (2), samplers (2), forwards (2: NumPy, external), source types (6 readers), checkpoint dtypes (5). Nowhere else.

The one structural finding that changes a task's scope: **Saluki breaks "one dtype per checkpoint, found from the file's size"** (`checkpoint_dtype()`), because its 851 tensors are of 12 types. The design therefore makes the dtype a property of each tensor in the layout table (the `Tensor.kind` the plan already carries per tensor), not of the file. That must be decided in T359, before T363.

## 1. The frame: layers and direction of imports

Proposed layers (lower never imports upper):

- **L0 descriptions (data, no I/O):** `engine/layout.py` (tensor table per layout), dtype registries, `shaders/` manifest, contracts (plan, messages, GPU protocol), `src/models/` list.
- **L1 computation:** kernels, `engine/` NumPy forward and layers, `convert/` readers and writer, `forward/engine.js`, `gpu/`.
- **L2 conduct:** `worker/` (load, convert, generate), `forward/choice.js`, `forward/threads.js`' search, `forward/gpuside.js`.
- **L3 screen:** `src/page/`, `src/benchmark/`.

Where today's code goes against this (verified by the import lines):

- `public/convert/*.py` imports the *window* `llama2_numpy` in 7 parts (`plan.py:4`, `checkpoint.py:8`, `config.py:5`, `conversion.py:4`, `gguf.py:9`, `tokenizer.py:6`, `readers.py:5`) instead of `engine.<part>`. A part reading another package through its Facade means the Facade can never shrink.
- `public/worker/ranges.js:7` and `sources.js:8` (fetching) import `weights.js` for `weightsRoom` (back-pressure of a model on the GPU alone): the fetch layer knows the GPU placement. Should be a callback passed in by the caller (`download(model, signal, { room })`).
- `public/forward/memory.js:8` imports `choice.js` for one constant (`GPU_BLOCK`); harmless, but the constant belongs with `BATCH` in `jobs.js`.
- No import cycles found in `worker/`, `forward/`, `gpu/` (tests already refuse them).

### (b) `Llama`'s mixins and where architecture differences live

**Today.**

- `class Llama(TensorOrder, Sampling, Generation)` (`public/engine/model.py:82`). Coupling through `self`, counted as distinct `self.<name>`:
  - `Sampling` reads 3 names (`vocab_size`, `greedy`, a buffer): it is already an independent object in a mixin's clothes, and it has two implementations (NumPy; `kernel_sampler`), chosen by assigning `self.penalize, self.sample = …` in `__init__`.
  - `Generation` reads 14 names: it is a loop over an interface (forward, forward_many, generate_many, tokenizer, sampler, stops).
  - `TensorOrder` assigns 37 attributes onto `self`.
  - `Llama.__init__` has 27 keyword arguments in four unrelated groups (tokenizer 7, architecture 13, runtime 4, text 3).
- The tensor order is written in **four** Python places, index-aligned by convention (AGENTS.md's pitfall says three; `conversion_plan()` is the fourth):
  - `public/convert/checkpoint.py` `layout()` — shapes and matrix/vector/table.
  - `public/convert/plan.py` `conversion_plan()` — source names and transforms, one list entry per `layout()` entry.
  - `public/engine/tensors.py` `llama_/gpt2_/qwen35_/lfm2_tensors()` — attribute names.
  - `public/engine/checkpoint.py` `checkpoint_dtype()` — sizes.
- JavaScript re-derives parts of it from the header:
  - `forward/memory.js`: `layerSlots`, `linearWidths`, `rotatedWidths` (copies of `engine/layers.py:123,117,282`), `footprint()`'s `tables` and dtype ratios.
  - `forward/alone.js`: `gpuBytes()` (`(arch === "llama" ? 3 : 2) * hidden * dim`), `GPU_ALONE`/`LAYER_MATRICES` by name, `gpuOnlyUnfit()`.
  - `worker/weights.js:225` builds a form by hand with 4 of FORM's 7 keys.
- `external_tensors()` (`model.py:51`) answers for `arch == "llama"` only, by building a half-initialised `Llama` with `Llama.__new__` and calling the mixin on it. This is why `gpuOnlyUnfit()` refuses every other architecture with the text "only a Llama's tensors are [placed], by external_tensors()": a limit of the code's shape shown to the visitor as a property of the model.
- Branch counts (code lines, comments excluded):
  - Python: 73 architecture/`model_type` comparisons (`config.py` 22, `gguf.py` 19, `model.py` 9, `plan.py` 8, `engine/checkpoint.py` 4, `convert/checkpoint.py` 4, `conversion.py` 3, `tensors.py` 2, `stream.py` 2) and 104 trait conditionals (`model.py` 36, `layers.py` 20, `config.py` 13, …).
  - JavaScript: 8 `arch` comparisons (`memory.js` 3, `engine.js` 2, `alone.js` 2, `worker/weights.js` 1) and 70 trait conditionals (`engine.js` 25, `memory.js` 19, `gpu/block.js` 8, `gpu/tokens.js` 7, `gpuside.js` 6, …).
- What one architecture cost: `lfm2|convolution` is named on 126 code lines in 18 product files; `qwen35|linear` on 171 lines in 19 files (outside `/benchmark/` and `shaders/`).
- `forward/engine.js`'s `run()` (lines 399–480) is already feature-driven rather than `arch`-driven: `bq`, `qNorm`, `wg`, `turns[l]`, `layerNorm`, `parallel`, `lines[l]`, `linear`/`convolution`, `rotated`, `positions` — 10 flags in one loop.

**Proposed form.**

*(b1) Layout table — Strategy, 4 implementations × 4+ consumers.* `public/engine/layout.py`: for each of the four layouts (`llama`, `gpt2`/`neox`, `qwen35`, `lfm2`) one function returning rows `(name, role, shape, per)`.

- `role` is `matrix` / `vector` / `table` (left out when quantised) / `embedding` / `classifier`.
- `per` says which layers the stack covers (`every`, `attending`, `stateful`).
- Derived from it: `layout()`, `tensor_bytes`/`checkpoint_size`, the engine's attributes (the three `*_tensors` methods and `TENSOR_NAMES` go), `checkpoint_dtype()`'s sizes, `external_tensors()` for **every** architecture, and the per-layer kinds (`layer_slots`).
- The dtype is chosen **per row** by a function of the row (today: every matrix the file's dtype, vectors float32, tables float32-or-absent). That is the hook Saluki needs.
- The engine owns the format; `convert/` imports `engine.layout` directly.
- `conversion_plan()`'s source names stay with the family (next point) but are keyed by row *name*, not by list position, so the two can no longer drift.

*(b2) Families — Strategy by `model_type`, about 10 entries over 4 layouts.* `public/convert/families/` (`llama.py`: llama, mistral, qwen2, qwen3, granite, smollm3; `gpt2.py`: gpt2, gpt_neox; `qwen35.py`; `lfm2.py`). Each provides what today is spread over six functions: `normalize(config)`, `check(config)`, `form(config, source)`, `sources(...)` (Hugging Face names and transforms by row name), and the GGUF side (architecture name, metadata → config, tensor names, `agrees`). `config.py`, `plan.py`, `gguf.py` keep the shared flow and look the family up. Granite and SmolLM3 are entries that adjust a Llama's config, not new layouts — the table must allow a family to be "llama plus these four numbers" without a class.

*(b3) `Llama` by composition.*

- `Sampler` with two implementations (NumPy, kernel).
- The forward with two implementations: `NumpyForward` (owns `key_cache`, `delta_state`, `conv_state`, `follow()`); `ExternalForward` (owns the plan and the JS engine).
- A generator that takes those and the tokenizer.
- `Llama` stays the Facade the worker and 81 test files use, with the same keyword arguments (it is a public interface; changing it buys nothing). Inside, the arguments are grouped once into a form, tokenizer options and runtime options.
- The three base classes go. `Llama.forward`, `Llama.generate`, `Llama.greedy`, `sample`, `penalize` remain as attributes that delegate, because tests replace them (3 `monkeypatch`/`Llama.<method>` sites in `tests/*.py`).

*(b4) The JS engine — Strategy only for the three things that have ≥ 2 implementations.*

- Layer mixer (`attention`, `linear`, `convolution`: 3), FFN (`swiglu`, `gelu`: 2), norm (`rms`, `layer`: 2). `createForward()` resolves them once into per-layer arrays from `plan.layers[l]`; `run()` becomes `norm → mixers[l](…) → residual → ffn(…)`.
- The plan carries the per-layer facts (kind, place among its kind, whether RoPE turns it; later: window, RoPE table index, KV source, head size) and the widths, so the JS copies of `layerSlots`, `linearWidths`, `rotatedWidths` and all 8 `arch` comparisons go.
- **Per-block cost, said plainly:** up to 3 indirect calls per layer per block in place of 6–8 predictable boolean tests per layer per token. Against roughly 100 kernel calls per token (forward.js's own header comment) this should be invisible, but it is 未計測. It must be measured A/B in one process on tiny-lm (smallest model, largest relative overhead) before it lands.
- **What would overturn it:** a measurable slowdown. Then keep the single loop and move only the *facts* into `plan.layers` — that half gives most of the maintainability gain, and the dispatch is the cosmetic half.

*GPU side:* **do not abstract.** `gpuUnfit()`/`tokensUnfit()`/`gpuOnlyUnfit()` read the same plan facts instead of `linear`/`convolution`/`arch`. The fused layer in `gpu/` has one implementation; a Strategy there waits until T334/T344 give it a second.

**Behaviour / visitor.**

- Checkpoint bytes and options identical (b1, b2): no `CONVERTER` raise. If, while writing a family module, an option turns out to be wrongly computed today, it is numbered and goes to T369 rather than being fixed in place.
- Once `external_tensors()` serves every layout, GPT-2/NeoX become *eligible* for "on the GPU alone"; whether to switch that on is a separate decision (T226's note says no such model in the list is too large to hold twice). Keep the refusal, change its reason.

### (c) Dtypes

**Today.** Two different things share the word.

*Source types* (how a file stores a tensor; read to float32) — 6. Named in:

- `convert/gguf.py:27` `GGUF_TENSORS` (id → name) and `:263` (an error text listing the six by hand).
- `convert/readers.py:75-79` `READERS` (bytes per value, reader) and `BLOCKS`.
- `convert/stream.py:87-88,173-178`: three separate constructor arguments `bfloat16`, `q8_0`, `readers` for the kernel versions, with two special-cased `if info["dtype"] == …` lines.

*Checkpoint dtypes* (how the engine holds a matrix) — 5. `ternary` is named on 140 code lines in 32 product files, `int6` on 70 lines in 20. The sites, by kind:

- Sizes: `convert/checkpoint.py` `tensor_bytes()` (4 branches), `engine/packing.py` `stored_bytes()`/`group_of()`, `engine/checkpoint.py` `Places.take()` and `checkpoint_dtype()` (three hand-written size formulas), `forward/memory.js` `footprint()` (`128/36`, `32/28`, `32/36`), `forward/alone.js` `GPU_WEIGHT_BYTES`/`GPU_TERNARY_BYTES`, `src/models/memory.js` `SIX_OF_EIGHT`/`TERNARY_OF_EIGHT`.
- Writing: `Writer.write()` (4-branch if), `QUANTIZED`, `EITHER`, `check_dtype`, `dtype_name`.
- Reading: `Llama.__init__`'s `take()`, `engine.js` `weightAt()`, `matrix()` (`{int8, six, ternary}` booleans), embed.
- Kernels: `engine.js:298` (kind numbers 0/1/5/6/8/9/2 as literals), `jobs.js` `runner()` and `blockRows()` (`kind === 2`, `kind >= 8`).
- Lists of names: `worker/weights.js:104` `["int8","int6","ternary"]`, `worker/convert.js:145` `["int8","ternary"]`, `kept.js:43` `["int8","int6"]`.

**Proposed form — Registry, twice.**

- `convert/readers.py` → one registry of source types: `{name, ggml id, values per block, bytes per block, read (NumPy), kernel (name of the wasm export, optional)}`. `GGUF_TENSORS`, `BLOCKS`, the error text, the three Stream arguments and the three `kernel_*` functions collapse into it: the Stream takes one `kernels=` and the registry picks the kernel reader where one exists.
- `engine/dtypes.py` → registry of checkpoint dtypes: `{name, group(length), stored_bytes(count), suits(shape), pack(rows) → (bytes, scales), unpack(bytes), kernel packer name}`. `tensor_bytes`, `Writer.write`, `Places.take`, `take()`, `checkpoint_dtype()`'s size candidates and `QUANTIZED`/`PACKED`/`EITHER` read it.
- JavaScript keeps only what is JavaScript's: `jobs.js` gets the kernel side, `KERNELS = { int8: { relaxed: 0, plain: 1, rowBytes, sums: "int8_sums", quantize: "quantize_x" }, int6: {...}, ternary: {...}, float32: {...} }`, and `engine.js`/`blockRows` read it. Sizes come from the placed tensor table (each entry carries `kind`, `group`, row bytes), so the ratio constants in `footprint()` and `gpuBytes()` go.
- **`runner()`'s if-chain by kind stays an if-chain** (it runs per job per thread); only the literals get names. A table lookup there would be a change on the per-job path for no gain.
- The page's estimate (`src/models/memory.js`) runs without Pyodide and stays an estimate; its two ratios move to one constant table beside the list.

**Behaviour / visitor.** Nothing; converted bytes identical. The refusal for an unreadable GGUF type would be generated from the registry (wording may differ by a comma).

### (g) Failure handling

**Today — eight idioms (counted).**

1. Python `raise ValueError(text)` as a message for the reader: 31 in `engine/`, 61 in `convert/` (35 uses of the `refuse()` helper among them).
2. Python control exceptions: `Incomplete` (ask for more bytes), `Unsupported` (template).
3. JS `throw new Error(text)`: 15 in `worker/`, 8 in `forward/`, 15 in `gpu/`.
4. JS tagged errors by `Object.assign`: 4 sites, 3 tags (`pyodide`, `directLost`, `final`), plus reads of `error.status` (4) and `error.type === "Incomplete"` (2).
5. "Why not" values, `null` or an English sentence: `gpuUnfit`, `tokensUnfit`, `gpuOnlyUnfit`, carried on as `gpuWhyNot`, `tokensWhyNot`, `gpuReason`, `tokensReason`, `tokensWhy`.
6. GPU worker's `failed` / `unusable` / `ended` messages, the `lost` flag, `directLost`, the `cpuOnly` set, and the reload written twice as `if (!(await gpuOnlyReady(model, id))) return load(model, signal, id)` (`load.js:53` and after line 146).
7. The one catch in `worker.js:250-272`, which classifies by regex over message text (`/^pyodide\.ffi\.JsException: (\w+): (.*)$/`), by `err.type`, and by `name === "RangeError" && !/call stack/`.
8. Silent catches: 20 `.catch(() => {})`/`catch {}` in `worker/`, 2 in `forward/`.

Two open bugs live exactly here: T371 (the reason "the page is not cross-origin isolated" shown for `?threads=1` — one reason text standing for two causes) and T377 (`room()` does not see `lost`).

**Proposed — one carrier, no hierarchy.**

- `public/failure.js`: `class Failure extends Error` with `kind` (`refused`, `memory`, `network`, `gpu-lost`, `cancelled`) and optional `retry` (`"cpu"`, `"again"`).
- The three ad-hoc tags become kinds.
- `failureOf(err)` is the one place that reads Pyodide's `JsException` text; `worker.js`'s catch switches on `kind`.
- Python keeps the convention "ValueError = text for the reader" (it works, and 92 sites follow it).
- One `fallBackToCpu(key, why)` in place of the two reload lines and `onLost`.
- The "why not" values stay values (they are not errors), but their texts move into one table so that one cause has one text.

**Visitor.** Nothing; every text kept byte for byte (which tests assert on texts I did not enumerate — unverified).

**Measures.** Idioms 8 → 4 (ValueError; `Failure`; reason values; GPU worker messages). Places that decide "is this a memory failure": 1 (as today) but by `kind` where the error was made in JS.

**Task.** New **T380**, after T368 (the `kind` is a union type), small; T371 and T377 are fixed in it or just after. Lowest priority of the seams: no touchstone needs it.
