### `/benchmark/`

- **ページの部品は聞いて描くだけ（T643.11）。** 節の Markdown・状態（ok・none・wrong・error）・`said` と報告の組み立ては `src/bench/` の純な関数（`deviceResult()`・`cpuResult()`・`storageNone()`・`storageResult()`・`lineResult()`・`gpuNone()`・`gpuResult()`・`gpuMarkdown()`・`reportOf()`）で、`tests/bench.ts` が作り物の答えで直に試す。ページの文として読むのは配線（どの関数に答えを渡すか）だけ。表や判定を足すなら `src/bench/` に置く（DOM・Worker・`localStorage` を読まない）。節の結果の `data` は節ごとの型（`src/bench/sections.ts` の `SectionData`。結果の型は `Result<"cpu">` のように節の名前で、ページの持ち主の `results` は `Results`）、状態の語は `STATE` の 1 つの表（`shown` は札と報告の題、`said` は「the CPU section …」と節ごと失敗した警告）。GPU の節が名指すモデルの形は `src/runtime/benchmark/gpu/models.ts` の `MODELS` の 1 か所（Worker の段と、ページの bandwidth の行列 `BANDWIDTHS`・量子化の行の数。何も import しないのでページも読む）。表の行を切るのは `cellsOf()` の 1 か所（ページの `rendered()`・`warnings()`・報告の読み）。**節の要素は `benchmark.astro` に手で書く**（`<section data-section="名前">` と最初の `<h2>`、`about` の文は持ち主のもの）: 節を足す・題を変えるなら `src/bench/sections.ts` の `SECTIONS`・`TITLES` と一緒に（ずれは `tests/bench.ts` が落とす: 要素の名前と順が `SECTIONS`、`<h2>` が `TITLES`。T643.16）。
- **GPU の節の段は表（T643.12）。** ページが頼む段の並びは `src/bench/gpusection.ts` の `gpuPlan()`（アダプタの答えと頼むモデルから、名前と知らせの組の並び: 数えてから 1 つ目を頼むので「N / N」は数え違えない）で、答えは段の鍵で持つ（`GpuFound`: 1 回の段はその鍵に、`bandwidth` と `token` は頼んだ順の並びに。`gpuKept()`）。表と要約（`gpuMarkdown()`・`gpuSummary()`）は鍵で読み、段の名前（訪問者に見える進みの文と表の列）を比べない。Worker の窓口（`src/runtime/benchmark/gpu.ts`）は表 `STEPS` を引くだけで、表に無い段は失敗で答える。**段を足すなら**: 契約の `ToBenchGpu` と `BenchGpuResults` に 1 行（`STEPS` の書き忘れは tsc、鍵の突き合わせは `bench-modules-check`）、`STEPS` に 1 行と自分のファイル、`gpuPlan()` に 1 行、表は `src/bench/` に置いて `gpuMarkdown()` から鍵で読む。
- **計測のページは 1 つ（T134）。** 節は止まっても次へ進む（節の Worker が 5 分何も言わなければ failed）。**報告の URL は GitHub のログインの飛び先にして 7,000 文字まで**（超えると return_to が黙って落ちる: 超えたら要約 `shortReport()` で、全文はクリップボードから）。
- **警告は報告の頭に 1 か所（T227）。** `warnings()` は節の行を WRONG・failed・unsteady・skipped の語で拾うので、**ページに失敗を書くときはその語のどれかを入れる**（使わない所は `said` で渡す）。
- **節の進みの知らせは `{stage, at, of}`**。**Worker に答えでない知らせを足すときは、`ask()` の除く条件に入れる**。回線を絞る形は応答の本文を決めた速さでしか読まない（WebKit は読まれなくても受け取り続けるので絞れない）。実行中は Screen Wake Lock を頼み、隠れていた秒は報告の頭に 1 行。
- **「GPU ÷ CPU」は CPU の節の実測と比べる（T157）。** 1 トークンは GPU の各モデルの重みの GB を CPU の節の GB/s で読む時間、プロンプトは同じ作り物の ms / トークン。デバイスを失った後・フォールバックのアダプタ・WRONG の形では比を出さない。**モデルの節はページの本当の経路を測る**（T184・T190: 最初の読み込みの上で、64・256 トークンのプロンプトを選び方のまま・CPU だけ・GPU だけで交互に、書くことを本数ごとに 3 回ずつ。本数はモデルのページの覚えた本数）。
- **GPU の節の計測の決まり**: n と 2n の差で取り、形を交互に測る。コピーを 128 MiB 以上置いて順に読む。測る道はエラースコープの中に（断られた submit は時間がかからない）。**ビット一致を求めてはいけない**（WGSL は並べ替えを許す）。Chrome の timestamp-query は 65.5 µs の倍数に切り捨てる。
- **GPU の節も端末の機能をエンジンの `deviceFeatures()`（`shaders/key.ts`、窓口の `shaders.ts` から）で読む**（T642.17: `gpu()` が装置を開いた後に 1 回、`shared.features` に。プロンプトの形は `half`・`shuffles`・`packed`、attention・答えのステップの層・mul_mat_vec の subgroups は `subgroups`（装置の subgroups と WGSL の `subgroup_id`）、DP4A は `packed`）。`navigator.gpu.wgslLanguageFeatures` を直に読むのは報告の `wgsl` の一覧だけ。ベンチだけが読む機能（`timestamp-query`）は装置に直に聞く（上限の節の f16 も `features.half`）。**どの機能の組でどの形を出すかは `tests/bench-features-check.ts`**（軽い組: 偽の装置で info・bandwidth・prompt・layer・layer steps を 8 通りの組で。subgroups があって `subgroup_id` の無い装置が `shuffles` と `subgroups` の取り違えを見分ける唯一の組）。
- **GPU の節の行列 × ベクトルのうち 2 つはエンジンの文そのもの（T624.2、2026-10-31、持ち主の決め）**: 「llama.cpp mul_mat_vec (engine)」と「ORT DP4A small M (engine)」は `fusedMatVec({ input: "plain", output: "write" })` と `fusedDp4aMatVec({ output: "write", weights: "int8" })`、層の表の separate steps の積と alone も同じ文（`layerparts.ts` の `plainProduct()`）。束縛はエンジンの形（Params が 3・ベクトルの尺度が 4・出が 5）で、エンジンの文に `first` は無いので出を塊の最初の行から束ねる: 塊は 64 行の倍数で切る（`placed()` の `CHUNK_ROWS`、束ねる位置の揃えは最大 256 バイト）。**T624.2 より前の報告のこの 2 つの数（ベンチの写しの文）とは比べない**。ベンチだけの文は `shaders/matvec.ts` の MMVQ と ORT MatMulNBits の 2 つ。CI の SwiftShader は GPU の節で速さを測らない（正しさだけ: `bench.yml` の前後の数は無い）。
- **3 値の行（T270）**: GPU の節の最後の段 `ternary`（`gpu/ternary.ts`）が、答えのステップの行列 × ベクトル（Llama 3.2 1B の w1 と Ternary Bonsai 8B の w1）を int8 のエンジンの DP4A・3 値のエンジンの文（符号を −1・0・+1 に直す）・3 値の −Σa の形（`shaders/matvec.ts` の `TERNARY_SUMS_MATVEC`: 符号を 0・1・2 のまま掛け、ベクトルを読み込む所で 16 個ずつの和を作って行の点ごとに引く。ベンチだけの文で、目録 `shaders/engine.ts` に無いので端末の鍵は動かない）で、プロンプトのタイル（エンジンの `promptForms` の int8 と 3 値の DP4A、64 トークン）と層（T175 の融合した DP4A の層の行列だけを 3 値の文に替えたもの）を int8 と並べて交互に測る。3 値の 2 つの行列 × ベクトルとタイルは JavaScript と比べてから測り（`checkTernary()`: 段 `check` も同じ関数を呼ぶので、CI のフォールバックのアダプタでも正しさが分かる）、WRONG の形は測らない。層は検査しない（行列の読みはエンジンの行列 × ベクトルの検査が持ち、層まるごとは gpu-check が持つ）。ページの表は `src/bench/ternary.ts`（× int8 は同じ表と形の int8 の行に対して、タイルは subgroups の有無の同じタイルに対して）、要約の 1 行は「−Σa の形 ÷ エンジンの形」。**どちらの形が速いかは持ち主の端末の報告で決める**（T232 の覆す条件）。`/benchmark/` のワーカーで `fusedDp4aMatVec` に `"ternary"` を頼んでよいのは `gpu/ternary.ts` だけ（`bench-modules-check` の `TERNARY_ASKING`）。CPU の節の最後には、同じ w1 の形で 1 本のカーネル（`matmul_t2r`・`matmul_t2`・`matmul_t2r_tile` の 16 トークンを `matmul_q8r`・`matmul_q8`・`matmul_q8r_tile` と並べて）と、回した基底の回転（`rotate`、幅 5120 と 17408、塊 1024）を、モデルのメモリの重みの所を書き潰して測る（新しいメモリを取らない: T96。`sections.ts` の `kernelRows()`、表は `src/bench/cpu.ts` の `kernelsTable()`）。数は未計測。
- **CI はふだん軽く、毎晩全部（T193）。** デプロイの軽い組で確かめられないものは次の毎晩の全部の組で確かめる。schedule の run は main のワークフローの版で走り、失敗の通知は cron の行を最後に変えた人に行く。
- **ラウンドのずれ（T555）**: 既定のラウンド（`ROUNDS`）は最初の組を頭に 2 回と最後に 1 回走らせ、最後 ÷ 2 回目の速さを表の下に 1 行（`drift()`）。1 回目は比べない（冷えていて、stories260K で最後の 5 分の 1・llm-jp-3 150M で 0.9 倍）。線 `DRIFT_LINE` 0.9 を下回ると語「unsteady」で警告に入る（線は仮: 持ち主の端末の報告で決める）。比には間の重いラウンド（NumPy の float32）の後の熱も入る（それを見るためのもの。そのラウンドを飛ばす端末では小さく出る）。小さいモデル（stories260K）では 64 トークンが数十 ms で、比は雑音（138% が出た）。
- **メモリを言わない端末は NumPy のラウンドを飛ばす（T214）**（iPhone でモデルの節の峰がタブを落とした）。 Page memory の節（T173）は 64 MiB ずつ伸ばし各段の前に `sessionStorage` に印を書き、読み込み直したページが印を見つけたらそれを上限として出す（iOS は例外を出さずにタブを落とす）。Run all には入れない。
