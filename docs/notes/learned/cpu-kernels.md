計測環境: 2026-09-26 までの「この開発機」は ARM big.LITTLE（Cortex-A78×4 + A55×4）、メモリ約 6.6GB・スワップなし。2026-09-26 からは a1-free（OCI の Ampere A1、Neoverse-N1 × 2、メモリ 11.9GB・スワップ 4GB、Ubuntu 26.04.1）。どちらも Node 24。**変更の前後を 2 つの機械の数字で比べない**。モデルごとの数字の表・run の ID は `docs/tasks/T番号.md` と `docs/notes/` にある。

### CPU のカーネル

- **上限と監査（T158、表は `docs/notes/t158-cpu-audit-2026-09-27.md`）。** a1-free の V8 の上限: 読み出しだけ 11.8 GB/s、`relaxed_dot` + 2 つの load 33 G MAC/s、レジスタだけ 69、f32 の mul + add 8.8〜8.9。持ち主の Android は 1 トークン 1 本 12.9〜18.9 GB/s・4 本 27.6〜28.7。1 トークンの生成は帯域の壁（`matmul_q8r` が DRAM の読み出しの 97%）。上限のループは `kernels/ceilings*.ts` で、`/benchmark/` の CPU の節が同じメモリの上で測る。**上限のループは検算で見張る**（戻り値を捨てたループは消える）。**ループの定数は呼び出しから渡す**。
- **カーネルの形の決まり。** (1) x86-64 と arm64 の両方で測り、的の arm で決める（x86 で速い形が arm で 0.55〜0.6 倍のことがある）。(2) 4 つずつの道と残りの道の試験は残りが 0〜3 のどれも通る幅で。(3) ビット単位で同じと言う変更は厳密な比べも回す（`attention-compare.ts --exact`）。
- **入れたもの**（数字は各タスク）: attention の score を 4 位置ずつ、swiglu と gelu を `vexp` で 4 つずつ、int6 の広げを 8 命令に、プロンプトの 4 行 × 4 トークンのタイル `matmul_q8r_tile`、relaxed の補正をグループの整数の和に畳む、sample のカーネル、**`matmul_q8r` のスケールを 4 グループで 1 回に**（T167: 1 本では CPU で 0.88〜1.18 倍と割れるが、既定の本数ではどの CPU でも遅くならない）。
- **forward.ts の外の費用（T164）。** llm-jp-3 150M で 3.5〜4.1%、tiny-lm で 16〜20%、その多くが `sample`。Python から JS を呼ぶ 1 回は 1.3〜1.7 µs。
- **サンプリングの決まり。** kernel（`sample`・`penalize`）・NumPy・JavaScript の模型（`walkLikeCpu`）は同じ形（smoke が見る）。(1) top-p の足切りの線は「いちばん大きい確率」で抑える。(2) **最大の logit が有限でない logits からは引かず、エラーで止める**（kernel は −1、エンジンは `ValueError`（`NOT_FINITE`））。(3) **top-k・min-p・presence penalty（T274）**: 順は「top-k → top-p → min-p」、presence penalty は**書いた語のうち**直近 64 語から（プロンプトの語は数えない）。top-k があると確率の大きい順に歩く（無いときは添字の順のままで、今までの種は同じ文を書く）。**同じ確率の語は添字の小さいほうが先**（T561: top-k の境でも、大きい順に歩くときも。kernel・NumPy・`likecpu.ts` が同じ語を引く。kernel は確率が等しいときだけ添字を読むので速さは同じ）。greedy は top-k と min-p を見ない。GPU の SAMPLE にもある（T546）。
- **3 値の dtype とカーネル（T230・T231・T533）。** `ternary`: 128 個ごとのグループに 32 バイト（2 ビット、並びは PQ2_0）と **float16 のスケール**（並びは「値の全部、そのあとスケールの全部」）。**変換は丸めない**（`ternary_x`: 0 でも ±スケールでもない値、float16 が持てないスケールは断る）。一覧の項目の `weights: "ternary"` でページが名指しで頼む。カーネルは 2 ビットを広げず、活性値を 1 トークンに 1 回並べ替える（`interleave`）。スケールは 4 グループぶんを 1 回で広げる（`halves4`）。GPU は上げるときに float32 に広げる（`scalesIn()`）。
- **1 ビットの dtype とカーネル（T634）。** `binary`: 128 個ごとのグループに 16 バイト（+1 で立つ符号、ggml の Q1_0 と同じ 18 バイト）と float16 のスケール、並びは 3 値と同じ「値の全部、そのあとスケールの全部」。**群の 16 バイトは Q1_0 の並びでなくカーネルの並び**（重み 64 h + 4 c + p が c バイト目の 4 h + p ビット目: `pack_binary()`）で、シフト 1 つとマスクで `interleave()` の面と同じ並びの符号になる。符号 2 b（0 か 2）は 3 値の符号 w + 1 と同じ数なので、活性値は 3 値の用意（`takes: "interleaved"`）を分け合い、**同じ重みなら 3 値の道の logits とビット単位で同じ**（`tests/binary-same-check.ts`、`ternary-check.ts` がカーネルどうしを）。**カーネルは 3 値と 1 つ**（T644.7: 詰め方を型引数 `Ternary`・`Binary`（`kernels/signs.ts`）で渡す `signsRows<P>`・`signsTile<P>` を、`matmul_t2`・`matmul_b1`（`kernel/matmul.ts`）と relaxed の 4 つ（`relaxed/signs.ts`）が呼ぶだけ。符号だけの詰め方を足すなら `signs.ts` にクラスと、`groupBytes`・`rowBytes`・`blockBytes`・`codesOf` の枝）。**変換は丸めない**（`binary_x`: ±スケールでない値は断る。0 は群の全部が 0 のときだけ、+0 として持つ）。**GPU では 3 値の符号として持つ**（T634.3: `PACKED` の `gpu.as` は `ternary`、`gpu/packings.ts` の行の `on: "ternary"`・`spread`。上げるときに GPU の Worker の JavaScript が 16 個の表で広げる `spreadBits()`、GPU だけのモデルは届くままに `routedBits()`。シェーダの文は 3 値のもので、端末の鍵も 3 値の `keys.ternary`。GPU の上の大きさは 3 値と同じ。**シェーダの選びは詰め方の名前でなく `asTernary()` で**: 名前で `=== "ternary"` と比べると binary が int8 の文で掛けられる）。**速さは 3 値と同じ**（`tests/ternary-bench.ts --signs`、CI の 6 つの形: 1 本は 1.00 倍、4 本は x86-64 1.02 倍・arm64 1.06 倍。読む量は半分でも 1 本では計算が律速）: 得はメモリ。`ternary-bench.ts` の Worker は argv を持たないので、旗で表の中身を変えない（変えるなら番号のそろう形で）。
- **llama.cpp の塊のカーネル（T363.4）。** Saluki の 10 種類の型を詰めたまま掛ける。**重み = F·S·W − Fm·M**。32 個の群の和 G = Σ S·W·a を整数で厳密に作り、float32 の手順は 1 つなので、relaxed の有無・1 トークンかタイルかで数が変わらない。`matmul_sbw_tile`（符号を重みに置く）は **relaxed SIMD の決まっていない動きに乗る最初のカーネル**: `signed_dots` が真の所でだけ呼ぶ（CI の arm64 の 3 エンジンは真、x86-64 は偽）。`sb_row` は 1 行を float32 に（読み手とビット単位で同じ）、`sb_tables` はチェックポイントの `codebooks` の行からカーネルの表を実行時に作る（ファイルの形式にカーネルの都合を入れない）。別のモジュールなので塊のモデルのときだけ取る。表は `kernels/README.md`。
- **小さいモデルの形の比べ（T513、docs/notes/t513-quant-combos-2026-10-15.md）。** 350M〜E2B では **int8 がいちばん速い**（6 ビットは 0.52〜0.74 倍、Q4_K_M の塊は 0.76〜0.88 倍）。塊の得は取得とメモリだけ。ふつうの Q4_K_M は塊のまま残らない層（Q6_K・Q5_K）を持ち、その束は int8 に広がる。幅が 256 の倍数でないモデルでは塊はほとんど残らない。
- **attention の点数の頭打ち（T612: Gemma 2 の `attn_logit_softcapping`）。** 点数を √head で割った後に cap · tanh(s / cap)。計画の `score_softcap`（0 は無し、options の名前も同じ: logits の `softcap` と並ぶ設定）、NumPy の forward は点数の行列に掛ける。カーネルは別の export `attention_capped`・`attention_f16_capped`（仕事の種類も別、頭打ちの値は仕事の out stride の欄）: `attentionOf<T, C>` の 2 つ目の型で畳むので、**今までの `attention`・`attention_f16` は命令単位で同じ**（`kernels-same` は export と型の増えたことだけを言う）。tanh は 1 − 2 / (exp(2s / cap) + 1) を `vexp`・`fexp` で（4 つずつと残りはビット単位で同じ）。`attention-check` と `kernels-in-browser.ts` が float64 の式と見る。GPU には置かない（`REASONS.scoresCapped`、`gpuFit()` の `scoresCapped`: シェーダに足すと端末の鍵が動く）。
- **回した基底（T237）。** Bonsai 2 27B の行列は R = H S（S は入力の値ごとの符号、H は 1024 個の塊ごとの Walsh–Hadamard）として W R⁻¹ で入っていて、forward は R x に掛ける（`engine/layers.py` の `hadamard()`、`FORM` の `rotated`）。カーネル `rotate`・`unrotate`。重みの側には畳めない。外れ値の列は使わない。**GPU（T271.1）**: 行列の入力を回して 8 ビットにするのを 1 つのディスパッチ `ROTATE_QUANTIZE` で（`QUANTIZE` の代わり。1 トークンのディスパッチの数は今と同じ）、GPU が埋め込む行は `UNROTATE` で戻す（`shaders/rotate.ts`: CPU のカーネルと同じ float32 の演算を同じ順で、量子化は `QUANTIZE` の詰め方と尺度の語）。だから回した基底のモデルは詰めた形だけを選ぶ（プロンプトのタイルは `packed`、答えのステップは DP4A の「the norms apart」）。符号は幅ごとに計画の `rotated.signs`、どの量子化も `m.block.quantizing()` が基底で選ぶ（種類の入力も）。`wb`・`wa`（linear の層のゲートの小さな行列）は回して入っておらず、回さない入力を読む（CPU と同じ）。
