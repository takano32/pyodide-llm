### WebGPU

- **方針の経緯。** バッチ 1 の生成をそのまま移した形では持ち主の 3 台で CPU に勝たなかった（1 トークンに約 18〜20ms の固定費）。だからプロンプトから GPU に置き、生成は融合とまとめ読みで。**生成の勝ち目は GPU と CPU の帯域の比で頭打ち**（持ち主の Android で 1.39 倍）。
- **プロンプトを GPU で（T135）。** ロジットの要らない `forwardMany` のブロック（64 トークンまで）。**橋渡しは GPU の Worker と共有メモリ**: 頼みは `postMessage`、答えは制御領域の語（`GPU_DONE`・`GPU_FAILED`、働いている間は `GPU_BEAT`）で、`forwardMany` は `Atomics.wait` で待つ（`Atomics.waitAsync` は Firefox 141〜144 に無い）。10 秒印が動かなければ GPU をやめて CPU でやり直す。**GPU は自分の K と V を持つ**（CPU のキャッシュと同じなのは位置 `gpuEnd` まで）。置くのは層の行列（詰めた値とスケール、チェックポイントと同じ並び）と norm で、埋め込みの行は CPU が引き、RoPE の角はブロックの位置の行だけを送る。重みは WebAssembly のメモリと GPU の両方に置く（スマホと Apple は同じ物理メモリなので 2 倍）。GPU に回すのは、隔離されたページ・詰めた重み・head の大きさが 4 の倍数で flash attention のタイルが workgroup のメモリに入るもの。モデルを替えると GPU の Worker は全部のバッファと device を手放して閉じる。回せないモデルと失敗は CPU のまま（ステータス行とコンソールに訳を 1 行）。**SwiftShader の速さは意味が無い**。
- **形は公開の実装から取り、端末で測って選ぶ（T146・T147、持ち主「既存実装の最高なやつパクらん？」）。** 行列積は llama.cpp・TensorFlow.js・ONNX Runtime Web の DP4A、attention は llama.cpp の flash attention のタイル。読み込みの時に候補を小さな行列で JavaScript と比べ、合うものを n 回と 2n 回の submit の差で交互に測る。覚えた形（`localStorage` の `gpu:<モデル>`）は端末の鍵が同じときだけ使う。**覚えるのは 4 つ**（`Remembered`: プロンプトの行列 `matrices`、プロンプトの attention `attention`、答えのステップの層 `tokens`、答えのステップの attention `tokenAttention`（T296））。覚えた形はそれだけをコンパイルして検査し、通れば測らずに使う。検査で落ちたら（同じ鍵の下でドライバが替わった）「remembered, but wrong now」と言ってほかの全部を選び直す。鍵を足すときは今ある覚えを無効にしない形で（覚えに無い鍵はその形だけ選び直す: T296 の前の覚えは行列と層を使い、attention だけ選び直す）。**計測の輪は `gpu/timing.ts` の 2 つ**（T642.5: n と 2n の submit の差の中央値 `pairedMs()`（プロンプトのタイル・答えのステップの attention）と、暖機の後の回の中央値 `roundsMs()`（ブロック・答えのステップの層）。呼ぶ側は記録か走りを閉包で渡すだけ）。**計測が読む時計はモデルの記録の `m.now`**（T642.4: `openDevice()` の 3 つ目の引数、既定は `performance.now`。`start()` の秒も同じ形で引数から）: `gpu/` の部品に `performance.now()` を直に書かない。検査は偽の装置の時計で「速い形が選ばれる」を見る（`tests/fakes/gpu-model.ts` の `costs`: ディスパッチのパイプラインごとの ms を submit のたびに足す時計。`overhead` は submit 1 回ごとの固定の ms で、n 回と 2n 回の差が打ち消すことを見るためのもの。`gpu-forms-check`・`gpu-tokens-check`・`gpu-start-check`）。
- **既定で GPU、端末で測って選ぶ（T148、方針 9）。** (1) **GPU を待たずに準備完了**（GPU の準備は裏で、その間のプロンプトは CPU）。(2) **フォールバックのアダプタ（`isFallbackAdapter`）は断る**。試験だけが許す（`gpuForce`、ページの `?gpuTest=on`・`fallback`・`always`・`only`・`quick`）。`requestAdapter` は `powerPreference` を付けない。(3) **ブロックごとに GPU か CPU か**（`promptTimes()`）: CPU は 16 トークンのブロックの ms / トークンの直近 5 つの下側の中央値、GPU は 16 と 64 トークンで測った直線。GPU が CPU の 0.95 倍より速いブロックだけ GPU。1 つのプロンプトは「GPU、そのあと CPU」の順にしかならない。測り直しは選ばなかった側で、プロンプトの一部だけ、8 回の生成ごと。ステータス行は判定が出たときだけ変わる。試験は `tests/gpu-default-check.ts`。持ち主の端末での選ばれ方は未計測。
- **生成も GPU に（T150〜T152）。** Python の `generate()` が `GPU_TOKENS`（4）ステップずつ `generateMany` に渡し、GPU は `EMBED` → 融合した層 → 分類器 → `SAMPLE` を 1 回の submit、ID と K・V を 1 回で読み戻す。**乱数は Python の生成器からステップの数だけ先に引く**。GPU が断れば（`undefined`）そのステップは CPU。層の形は `fusedMatVec` と `fusedDp4aMatVec`、attention はタイルか llama.cpp の flash_attn_vec。サンプリングは CPU と同じ乱数で同じトークン（ソートせず pivot の探し。top-k・min-p・presence penalty も同じ並びと線: T546。同じ確率の語が境にまたがると GPU はその全部を取る）。束ねる範囲の始まりは 256 の倍数が要る（stories15M は揃わず生成は CPU: gpu-check は揃わない最初の行列を `unbound()` で出して訳の文と比べる）。LayerNorm は行列の読みに畳めない。外れ値の列のあるモデルの分類器は float で掛ける。メモリを言わない端末（Safari・Firefox）でも生成を GPU に置く（T548、持ち主の決め。T205 で止めていた: iPhone の `/benchmark/` のモデルの節で、分類器と埋め込みも GPU に置いてタブが落ちた。持ち主の iPhone で落ちたら Safari だけ戻す。GPU が遅い端末はステップの計測で CPU に戻る）。
- **2 重に入らないモデルは GPU だけに（T156 の案 B）。** **読み込みの前に決める**（`weightsPlace()`）: 2 重が `deviceMemory` の半分に入れば両方に置いて測る（**8 と言う端末は 6.5 GiB まで**: 2B 以下は 2 重、3B 以上は GPU だけ）。入らなければ、`gpuOnlyUnfit()` が通すモデルは GPU だけ、それ以外は CPU だけ。メモリを言わない端末と 6 ビットは GPU だけにしない。**形**: 書き込みの 1 か所で層の行列と表（`gpuHoles()`）を GPU の Worker へ送り、残りを穴を詰めて WebAssembly のメモリへ（`placer()`）。書く側は 64 MiB より先に行かないよう `await` で待つ。CPU の速さは `/benchmark/` の CPU の節の値から見積もり、ページの使われ方（`gpu:usage`）で重みを付けた時間が GPU の 0.95 倍より短ければ CPU で読み直す（`aloneHolds()`）。**GPU が失敗したら CPU で読み直す**（この訪問のあいだそのモデルは CPU）。GPU の Worker は読み込みの前に開いてバッファを全部作り（`open()`）、届いた範囲を書く（`take()`）。CPU の側は何も動かない（スレッドは 1、CPU の forward は例外）。判定は読み込みの id をつけて送り、端末の鍵と一緒に覚える（ベンチの無い端末は GPU のまま）。HF の変換は届くままに OPFS へ書いて保存する（`keeper()`）。組み立ての前に終わる読み込みでは重みの `destroy()` が GPU の Worker を止め、次の読み込みは「ended」を待つ。GPU だけのモデルは表も K と V も CPU に持たない（T210。埋め込みの行は GPU で引く `EMBED_ROWS`。**分類器が別のモデルの見出しの語彙は負の数**）。**SwiftShader で GPU のステップを回す e2e は 256 トークンに 1500 秒を越える**（数トークンで確かめる: `models.yml` の `query=gpuTest=on&steps=40` など。**`steps` はプロンプトも数える**: プロンプトより短いと断られる。T577 から e2e は `steps=` のある問いでは長さの欄に触らない）。
- **次のモデルは GPU の Worker の後始末を待ってから読む（T205）。** `release()` が `ended` を待つ Promise を返す（最大 5 秒）。
- **有限でない値を断る（T219・T241・T243）。** `generateMany` は GPU の返した ID が語彙の範囲にあるかを見る。`SAMPLE` は logits の符号を除いたビットの最大で NaN と +inf を見る（**浮動小数で比べない**: lavapipe は `x != x` を畳む）。DP4A の量子化はグループの最大をビットの整数で取る。forward は書き戻しの float16 の指数のビットを見て、有限でない K か V のある頼みを断る。GPU だけのモデルは `OUTSIDE_VOCABULARY` で止める。
- **float32 → float16 の丸めは装置しだい（T225）。** WGSL は向きを決めない（lavapipe と SwiftShader は最近接、Direct3D（Windows の Chrome）と Linux の AMD の Mesa は 0 の向き。持ち主の NVIDIA の PC で層の検査が WRONG になったのは、参照が K と V を最近接に丸めていたため）。**実装に任された丸めの後の値は、参照が自分で作らずに GPU から受け取り、許される隣の値かを別に見る**（`heldHalves`・`heldFloats`）。0 の向きの装置は `tests/rounding.ts`。
- **gpu-check の線は自分の目盛りで。** float32 の形は E16、f16 のタイルは H16（重みと入力も float16 に丸めた NumPy: `K_HALF` 3 倍）、DP4A は Q8（プロンプトは `K_PACKED` 5 倍、答えのステップは `K_PACKED_STEPS` 3 倍: ステップの線はその run のプロンプトの距離も取る）で、層ごとに。**深い実物の DP4A は 8 ビットの丸めの境で層ごと・run ごとに違う層が線に近づく**（T562: 3 倍では正しい GPU が 1.39 倍まで出た）。1 層目の K と V の尺度 1 ± 1e-4。logits は最尤トークンだけ。**8 ビットの活性値の形は層ごとの小さな誤りを見分けられない**ので、形に依らないシェーダの誤りは float の形が捕まえる。CPU の誤差の比の線は誤った GPU を通した。行列を 0.3 で引いた作り物は DP4A の線が高くなりすぎるので、0.1 の `-calm` の作り物を足した。**線を決める前に、わざと壊した GPU がどこに出るかを NumPy で出せる**。
