### スレッドとメモリ

- **GitHub Pages のままでも cross-origin isolated にできる（T93）。** Service Worker が COOP と COEP（`require-corp`。`credentialless` は WebKit で効かない）を足すと、1 回の再読み込みの後どのブラウザでも隔離され、CDN の Pyodide と HF の Range も通る。
- **ソフトウェアスレッドは既定でオン（T93）。** Python の層のループを外すだけで 1.15〜1.42 倍。 **行列積の行を塊に刻んで取り合う形**（1 スレッドあたり塊 2 つ以上）ならコア数を超えても崩れない。**ソフトウェアスレッドごとに自分の番号で待たせ、名指しで起こす**。**取りまとめ役を Pyodide の居るメインスレッドに置かない**。検索の判断はコンソールの `threads:` の行に出る。
- **`WebAssembly.Memory` はモデルごとに作らず使い回す（T96）。** Chromium は 1 ページに 3 つ目を断った。`pooledWeights()`: 最大はモデルから決め（4 × ファイル + 1GB）、次のモデルが収まる限り使い回す。**最初から 4GB の最大で作ってはいけない**（スマホで Pyodide の予約が入らず黙って固まった）。後に別のモデルが続かない Worker は +1 GiB を予約しない（T242: ページが init の `ahead` にこれからの読み込みを並べる）。
- **段のやり直し（T120）。** ソフトウェアスレッドが止められたら、取りまとめ役は数えが 10 秒動かないところで諦め、その段を自分でやり直し、1 本で続ける。どの塊も自分の行だけを、変わらない入力から書くので同じ数を上書きするだけ。**状態を読んで書く段は、読む所と書く所を分ける**。
- **プロンプトのまとめ処理（T108）。** ロジットの要らないトークンは層ごとに最大 16 トークンをまとめて通す（`forwardMany`、Python は `forward_many`）。結果はビット単位で同じ。1 本ではほとんど効かず（1.16 倍）、スレッドと組むと効く（4 本で 2.91 倍）。活性値は「トークンごとの枠」に置く。attention もヘッドを段の仕事に分ける（T109: 長い文脈で 4 本が 1 本の 1.2 倍）。段の仕事の並びは `jobs.ts` の `WORK` と、`forward/threads.ts` の `softwareThreads()` の頭のコメント（仕事を組むのは `forward/engine.ts` の `jobOf`）。
- **KV の型。型を決めるのは `footprint()` の中の 1 か所**（エンジンと見積もりが同じ型を数え、worker は実際に取れたメモリで問い直して `external({ halfKeys })` で渡す: 渡さないと位置 2048 で 4 GiB を越える）。float16 の KV は読む量が半分だが広げに 2.4〜2.9 倍かかり、**GQA のモデルでは損**。**規則: 共有で GQA でなければ float16、それ以外は float32。ただし float32 で 32 ビットに入らない共有メモリ・もとから 64 ビットが要るモデルは float16。共有でないメモリでは float16 にすれば 32 ビットに入るときだけ float16**（float32 が 16 GiB に入らなければ float16）。GPU の K と V は float16（広げはカーネル `from_f16`: **試験の旗の後ろだけで通っていた道が既定の道になるときは、その道の速さを測る**）。footprint が大きくなるぶん GPU の門は GQA のモデルで少し厳しくなる。`halves4()` は half を符号つきで読んで 13 ずらし、AND 1 つと 2^112 の掛け算で広げる（65536 通りの全部で前の形とビット単位で同じ）。
- **forward が後ろに置くもの。** `footprint()` がヘッダから上限を出す（relaxed の補正（グループに 4 バイト）・外れ値の列・活性値の枠・RoPE の表・状態・KV）。**KV は 256 から倍々に、その場で伸ばす**（`grow()`: 層の塊を後ろから順に上げる。峰は文脈いっぱいぶんだけ）。`tests/memory-check.ts` が実物の確保と比べる（上回り約 1 MiB）。4096 位置の見積もり（GiB、共有）: Llama-3.2-3B の int8 は 4.20（64 ビット）、Qwen2.5-3B は 3.89（32 ビットに入る）、Qwen2.5 7B は 9.15。GPU だけのモデルの見積もり: Llama 3.2 3B は GPU だけ 4.109 GB（CPU だけ 4.746、2 重 8.834）。**作ったときに足りないと分かる共有メモリは共有でないメモリに替える**。
- **64 ビットのメモリの上限は 16 GiB（T129）。** 越えるモデルは `weightsBuffer()` が取得の前に断る（`pastWide()`）。文は持ち主の「This model is too large for a web page: it needs about N GB of memory, and a browser gives a page 16 GB at most.」。
- **Memory64（T101）。** AssemblyScript の Wasm64 の出力は `kernels/wasm64.ts`（asc の transform: Node が型を消して読む。T644.11 で `.mjs` から）が直す。64 ビットの上のカーネルは約 1 割遅いので 4GB を超えるモデルにだけ。番地は BigInt、**ソフトウェアスレッドへの仕事の表は float64**（32 ビットに番地を置くと上の桁が切れた）。
- **スレッドの本数の検索。** 1 回の比べは best・候補・候補・best の 4 つの塊（1 塊 5 トークン、頭の 1 つは数えない）で、判定は本数ごとの**下側の中央値**。下りで半分が速くなかったら 4 分の 1 も比べる。**覚える本数は GPU の準備と並ばずに測った答えだけ**で、前の訪問の本数はその訪問の最初の生成で検索し直す（その後は 8 回ごと）。鍵はモデルごと（`threads:<モデル>:<論理コア>:<メモリ>:<UA>`）。持ち主の Android の llm-jp-3 150M は 1 本 110・2 本 123・4 本 38.6・8 本 32.3 tok/s（CPU の節の作り物では 4 本が最速: 段の待ち合わせの回数が違うので、作り物は実物の本数を言わない）。帯域の広い機械ではスレッドがよく効く（CI の Linux ARM の 4 本で 2.06〜2.16 倍）、前の開発機では 1.2〜1.3 倍。Worker 間の `postMessage` の往復は 0.1〜0.3ms。試験は偽の時計（`createForward` の `clock`）。
- **変換したモデルの保存は OPFS（T99）。** 2 回目の準備完了は llm-jp-3 440M で 18.4 → 4.4 秒。保存の名前は `keptName()`（`?bits=` の dtype と、塊なら `:blocks`）、古い版と同じ項目の別の取り込み元の保存は `replaced()` が消す。
