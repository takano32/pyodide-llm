## 2. 質: K 量子化を広げて int8 に直す損（測った）

同じモデルの Q8_0 の GGUF と、小さい混ぜ方の GGUF を、それぞれ GGUF だけで int8 に変換して、ページのエンジン（カーネル、7 ビットの活性値、1 本）で同じ文の perplexity を比べた。文は Wikipedia の「Mount Fuji」「富士山」の最初の 1500 トークン。a1-free、Node の Pyodide 314.0.7。

| モデル | GGUF | 取得 | int8 | 英語 | 日本語 |
|---|---|---:|---:|---:|---:|
| Qwen3 0.6B（bartowski、`60b85c0e`） | Q8_0 | 805 MB | 846 MB | 25.604 | 33.586 |
| | Q4_K_M（Q4_K 71.5%・Q6_K 28.5%） | 484 MB | 846 MB | 27.531（+7.5%） | 37.913（+12.9%） |
| Qwen2.5 0.5B Instruct（bartowski、`41ba88db`） | Q8_0 | 531 MB | 556 MB | 19.931 | 24.029 |
| | Q4_K_M（Q5_0 51.0%・Q8_0 27.8%・Q6_K 10.6%・Q4_K 10.6%） | 398 MB | 556 MB | 20.507（+2.9%） | 24.685（+2.7%） |
| | Q3_K_M（IQ4_NL 46.8%・Q8_0 27.6%・Q4_K 20.3%・Q5_0 4.4%） | 355 MB | 556 MB | 21.299（+6.9%） | 25.768（+7.2%） |

**損はどこから来るか**（Qwen3 0.6B の英語、同じ 1500 トークン）: 同じ 2 つの GGUF を float32 に広げて NumPy で読むと（int8 も活性値の丸めも無い）、Q8_0 は 25.415、Q4_K_M は 27.459（+8.0%）。int8 にしてページの道で読むと 25.604（float32 から +0.74%）と 27.531（+0.26%）。**損は GGUF の量子化そのもので、広げて int8 に直すことで足されるのは 1% 未満**。

**読み方**: 小さい混ぜ方を選んでも、広げて int8 に直す今の道ではメモリは Q8_0 と同じで、得るのは取得の大きさ（60〜75%）だけ。質は 3〜13% 落ちる（0.5〜0.6B の小さいモデルでの数字。大きいモデルは未計測）。だから**同じリポジトリに Q8_0 が在れば Q8_0 を選ぶのが得**（T.505.3 の「どの量子化のファイルを選ぶか」の材料）。

## 3. 外した断り（T.505.2）と、残した断り

`Conversion.from_gguf()`（GGUF だけで開く道）だけ。原本の語彙つきの道（一覧の段 ②）は 1 字も変えていない。断りの文はどれも前のまま。

| 断り | 決め | 残る場合 |
|---|---|---|
| BOS を言わない GGUF | 書式（`tokenizer.chat_template`）が読めて、その頭が 1 つに読まれるトークンなら、それを頭のトークンにして開く（T.369 の決まりそのまま）。誰も名指さない 1 は config から外す: 書かず、止まりにも入れない | 書式が無い・読めない（jinja2 の取れなかったブラウザと、1 ターンを書けない書式）・文字で始まる。EOS を言わない GGUF |
| `rope_freqs` の表 | 表を頭のバイトから読み、llama3 の縮めの設定に読み戻す（`llama3_scaling()`）。その設定で作り直した表が 1e-5 で合うときだけ開く。表が頭に無ければ `Incomplete`（段取りが続きを取る: 表は最初のテンソルで数百バイト） | 最初のテンソルでない表（Swallow 8B の GGUF は最後: float32 のチェックポイントの RoPE の表は最初のテンソルより前に作るので待てない）、F32 でない表、llama3 のどの設定でも作れない表 |
| sentencepiece の語彙（`llama`） | 点数が sentencepiece の BPE の形（通常の語片の点数が全部整数で、半分より多くが別の値）なら、エンジンの `bpe` として読む。語片・点数・種類はモデルのファイルそのもの | 点数の無い語彙（全部 0・全部 −1000）、Unigram の点数、`add_space_prefix` が偽 |
| 前分割の名前 | `smaug-bpe`（Llama 3 の型、`ignore_merges`）と `deepseek-r1-qwen`（Qwen の型、NFC）を足した | 実物と原本で確かめていない名前の全部（`dbrx`・`glm4`・`llama3`・`falcon3` など）と、別の型の名前（`tekken`・`default`・`gpt-4o`） |

**表から読み戻す式**: 表は対ごとの角の割る数。速い対は 1、遅い対は factor、間は 1 / ((1 − s) / factor + s) で、s は対の周波数の 1 次式（s = (original / 波長 − low) / (high − low)）。だから factor は表の最大で、間の対が 2 つ以上あれば 1 次式が決まる。表に出るのは original / low と original / high だけなので low は 1 と置く（Llama 3 はどれも 1）。整数に丸めて表が合えば整数で言う。間の対が 1 つ以下なら Llama 3 の 4 と 8192 を試す。実物 2 つは config.json の数にちょうど戻った: Llama 3.1 8B は factor 8・high 4・original 8192、Llama 3.2 1B は 32・4・8192。

**sentencepiece の語彙で決めたこと**:
- GGUF は元のモデルが BPE か Unigram かを言わない。llama.cpp はどちらも「点数の高い対をつなぐ」で読む（Unigram のモデルには別のトークナイザになる）。ここは点数の形で BPE と分かるものだけを読む。
- **点数の無い GGUF が実物に在る**: `TheBloke/TinyLlama-1.1B-Chat-v1.0-GGUF` は 32,000 の語片の点数が全部 0（原本の `tokenizer.model` は −1、−2、…）。llama.cpp で開いても、つなぐ順は決まらない。断りを残した。
- **ダミーの空白は最初の文にだけ**。llama.cpp は特殊トークンの後の文にも置く。実物で比べた: Mistral 7B v0.2 はどちらでも原本と同じ ID（9/9）、Mistral 7B v0.3（`[INST]` がトークン）は、llama.cpp の読みだと空白が 2 つになり、同じ文を原本の `tokenizer.json` が読んだ ID と 0/9、置かない読みだと 9/9。
- 正規化（`precompiled_charsmap`）は GGUF に無い: 恒等（Llama・Mistral の語彙はそう）。NFKC の語彙を持つ sentencepiece の BPE のモデルが GGUF で来たら、正規化なしで読む（llama.cpp と同じ。見分けられない）。

**分かったこと**:
1. **Llama 3.1 8B・Llama 3.2 1B（bartowski）・TwIL-LM3（SmolLM3、`smaug-bpe`）は、tokenizer.bin も options も段 ② の変換と同じ**（`rope_scaling` も）で、ID は 9/9。
2. **Qwen3・Qwen2.5・LFM2.5 は tokenizer.bin が同じで ID は 9/9**。options の違いは `specials` だけ: GGUF は `<|fim_prefix|>` などを制御トークン（種類 3）と言い、変換器は「書式が書く特殊トークン」だけを残すので、打った `<|fim_prefix|>` は 1 トークンにならない（`tokenizer.json` はそれらを special でない追加のトークンと言い、段 ② は全部残す: T.143）。**これは T.505 の前からの GGUF だけの道の動き**で、変えていない。
3. **GGUF の中の書式は原本と違うことがある**。unsloth の Qwen3.5 4B は考えを空にする形（`<think>\n\n</think>\n\n`）、bartowski の Qwen2.5 0.5B の Q3_K_M だけ古いシステム文、MaziyarPanahi の Llama 3.1 は日付の無い古い書式、bartowski の DeepSeek-R1 Distill は `<think>\n` の無い書式。GGUF だけで開けば GGUF の書式に従う（ID が原本と違う行は全部これで、右の列は 9/9）。
4. **unsloth の Qwen3.5 4B の語彙は原本より 7 語多い**（248070〜248076 の音の語と、その後の詰め物 243）。先頭の 248,070 語片は原本と同じ。
5. **古い GGUF は表も縮めの設定も持たないことがある**: `MaziyarPanahi/Meta-Llama-3.1-8B-Instruct-GGUF` は `rope_freqs` もメタデータの縮めも無い。GGUF だけで開くと素の RoPE で動く（llama.cpp も同じ）。原本は llama3 の縮め（factor 8）。黙って違うが、GGUF が言わないことは読めない。
6. **`tokenizer.ggml.pre` の無い byte-level BPE の GGUF は、今までどおり GPT-2 の型で読む**（`MaziyarPanahi/Meta-Llama-3-8B-Instruct-GGUF`・`…Llama-3-8B-Instruct-64k-GGUF`・`…QwQ-32B-GGUF`）。Llama 3 と Qwen の語彙には誤った切り方（llama.cpp は「GENERATION QUALITY WILL BE DEGRADED」と警告して既定の型で読む）。T.505 の前は型で断られていたので見えなかった: **型を読めるようになって、この 3 つは誤った切り方で開く**。直す（断る）と今の GGUF だけの道の動きが変わるので、この回は変えていない（持ち主に選んでもらうこと）。
7. 止まり: GGUF だけの道は、GGUF の名指す BOS と EOS だけを止まりにする（Qwen3.5 は `<|im_end|>` の 1 つ）。llama.cpp は名前で拾った終わりのトークン（`<|eot_id|>`・`<|im_end|>`・`<|endoftext|>` など）でも止まる。変えていない。
