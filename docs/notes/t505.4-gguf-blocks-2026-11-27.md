# T505.4: int8 に広げると入らない GGUF を塊のまま開く（2026-11-27）

`?hf=` とシートで開く一覧に無いリポジトリのうち、int8 に広げると 16 GiB（64 ビットのメモリの上限、`forward/memory.ts` の `pastWide()`）に入らないモデルを、llama.cpp の塊のまま持つ道（`conversion.blocks`: Saluki 27B と一覧の 14B の GGUF と同じ形）で開く。

## 形

- 決めるのはページ（`src/page/repository.ts`）で、リポジトリのファイルの一覧（API の大きさ）だけから。変換器・段取り・worker・保存の名前は触っていない（`conversion.blocks` はどれも前から読む: 保存の名前は末尾に `:blocks`、`convert()` が塊のカーネルを先に取る）。
- `weightsOf(files)`: 重みの数の見積もり。量子化の札が 1 つの重みのバイトを言うファイル（表 `BYTES_A_WEIGHT`: 型そのもの F32・F16・BF16・Q8_0・Q6_K と、下で測った混ぜ方の Q5_K_M・Q4_K_M・Q4_K_S・IQ4_XS）のうち、`QUANTIZATIONS` の順で最初のものの大きさ ÷ そのバイト。
- `tooWide(files)`: 重みの int8 のバイト（`PYTHON_BYTES.int8 / PYTHON_WEIGHTS`、1 重みに 1.125 バイト）+ `BESIDE_WEIGHTS`（2 GiB: 4096 位置の鍵と値を float16 で、Qwen2.5 14B 0.8 GB・32B 1.1 GB、と残り）が `WIDE_BYTES`（16 GiB）を越えるか。重みを言うファイルが無ければ越えないと見る（前のまま）。
- `bestGguf()`: 越えるなら、`QUANTIZATIONS` の順で最初の「塊のまま持てる札で、塊のまま持った大きさ + `BESIDE_WEIGHTS` が 16 GiB に入る」ファイル。無ければ前のとおり最初のもの（worker が頭を読んだ後、重みを取る前に今の文で断る）。**順そのもの（`QUANTIZATIONS`、頭の 4 つは持ち主のもの）は変えていない**。
- `settled()`: 選んだか名指されたファイルが塊のまま持てる札で、モデルが越えるなら、項目に `conversion: { dtype: "int8", blocks: true }`。名指された Q8_0・Q6_K・Q3_K_M などは前のまま（広げる）。
- `choose.ts` の `urlLooked()`: URL が GGUF を名指す訪問（一度選ぶと URL に `&file=` が付く）も一覧を聞く（T505.3 では名指しなら聞かなかった）。聞けなければ前のまま名指しで開く。

## 数えたもの（huggingface.co の GGUF の上位 500、ダウンロード順、2026-11-27）

一覧を API で聞いた（1 回 1.2 秒あけて）。層の形が密なもの（`gguf.architecture` が llama・qwen2・qwen3・qwen35・gemma3・gemma4・mistral3 など）のうち、int8 で 16 GiB を越えるのは 52（gemma4 の 26B-A4B のような MoE を 4〜5 含む: 変換器が断る）。

- **いまの型で選べるもの 34、選べないもの 18**: 選ぶ札は IQ3_M 11・IQ3_XXS 7・IQ4_XS 5・Q4_K_M 4（14B）・IQ3_XS 4・IQ2_M 2・Q2_K 1。
- 選べない 18 の多くは、Q8_0・Q6_K・Q4_K_M だけのリポジトリの 27B〜33B（ggml-org・lmstudio-community・Qwen 自身・llm-jp-4 33B）と、K 量子化だけの mradermacher の 27B（Q2_K は Q3_K の行を広げて 1.6 倍になり入らない）。
- **Q3_K・Q5_K・Q6_K のカーネルがあれば**（見積もり: K 型の全部をファイルの大きさの 1.06 倍で持つと見た）、選べないものは 18 → 10、14B は Q4_K_M → Q6_K、27B の多くは IQ3_M・IQ3_XXS → Q3_K_M。**このタスクでは足さない**（取りまとめ役の決め）: 足すと一覧の `blocks: true` の項目（Qwen3 14B・llm-jp-3.1 13B など）の Q6_K の行が塊のまま残り、チェックポイントが変わる（`CONVERTER`、訪問者の取り直し、`loaded` の数、GPU の `SUPERBLOCKS` に足すかと端末の鍵）。Q6_K は重み 16 個の単位の尺度が符号つきの int8 で、群の整数の和が float32 で厳密な範囲（2^24）を越える（32 × 63 × 127 × 128）ので、今の算術の形のままでは入らない。別のタスクにした。
- 選べた 34 のうち実物で開けないもの: bartowski・mradermacher の Qwen3.8 27B は層 64（MTP の層）で断る（「model.layers.64.linear_attn.in_proj_qkv.weight is missing」）、unsloth の Gemma 4 31B は変換器が `TypeError`（`check_config` が層ごとの `head_count_kv` の配列で `%` を取る）。後者は文でなく例外の型が出るので別のタスクにした。

## 確かめ

- `tests/repository-check.ts`: 実物の大きさ（14B・32B・27B・12B）で、越えるかと選ぶファイルと `conversion` と保存の名前（`:blocks`）、名指しの 5 通り、何も入らない 72B、`WIDE_BYTES` を `pastWide()` に。壊し方 9 つ（越えないことにする・Q4_K_M を表から外す・blocks を頼まない・2 つの `BESIDE_WEIGHTS` をそれぞれ外す・最後のファイルで重みを数える・名指しの Q8_0 も塊に・入るかを見ずに選ぶ・16 GB と 16 GiB）は全部名前つきで落ちた。
- `tests/test_kept.py`: ページの頼みの形（GGUF だけ、`config.json` を名指して無い、`blocks=True`）で、段取りが `Conversion.from_gguf()` と同じバイトで塊を残す。
- 手元の Chromium（Playwright、ビルドしたページ、本物の huggingface.co）: `?hf=bartowski/Qwen2.5-14B-Instruct-GGUF` は一覧を 1 回聞き、URL が `&file=Qwen2.5-14B-Instruct-Q4_K_M.gguf` になり、塊のカーネル（8 つ）を取ってから Q4_K_M を取り始める（そこで閉じた）。`&file=` で名指した訪問も一覧を聞いて同じ。`?hf=LiquidAI/LFM2.5-230M-GGUF` は前のとおり Q8_0 を int8 に広げ、塊のカーネルを取らない。
