## 落とし方

- **tokenizer.bin の形式は変えていない。** 語片の点数に「その語片を作る最初の merge の順位 × −1」を書き、エンジンの今ある `kind="bpe"`（点数最大の対を合併、同じ点数なら左）で読む。byte-level BPE のとき（T63）と同じ手。語片は sentencepiece のつづりのまま（U+2581 は tokenizer.bin で空白になる: 今ある `tokenizer_bin()`）。
- **options に載るのは今ある鍵 2 つ**: `tokenizer_kind: "bpe"` と `prefixed`。`prefixed` に 3 つ目の値 `"never"`（どの文の前にもダミーの空白を置かない。復号も頭の空白を落とさない）を足した。normalizer に `Prepend` があれば `"every"`（今ある `prefixed_texts()`）、無ければ `"never"`。
- **対で合併するのと、つないだ文で合併するのが同じになる訳。** tokenizer.json の BPE は merges の名指す対だけを合併し、エンジンは「つなぐと語片になる隣どうし」を合併する。実物では (a) 語片を 2 つの語片に割る割り方は全部 merge、(b) merge が作らない語片は 2 つの語片でつづれない、が成り立つ（3 つとも破れは 0。transformers の `SentencePieceExtractor` がそう書き出す）。変換器が `merged_by_text()` で確かめ、破れていれば断る（`tokenizers` ライブラリで訓練した素の BPE は、語片ごとに割り方を 1 つしか名指さないのでここで断られる）。
- **残る理屈の上の違い（実物では 0 件）。** 本物は対の順位で、エンジンは語片の最初の順位で合併する。同じ点数（順位が入り交じる）の語片が重なって候補になると違いうる。CAT-Translate 7B は語片ごとに merges が並んでいて入り交じりは無い。Gemma は 87 語片だけが入り交じる: 全部が改行・U+2581・タブの並び（sentencepiece のモデルでは点数 0 の user-defined）で、ふつうの語片 255,474 個の点数は全部違う。作り物で点数を 64 個ずつ同じにすると 30,027 文のうち 63 文が本物と違った（4 個ずつ・16 個ずつでは 0）。
- **special でない追加のトークン**は今までどおり options の `specials` に入り（T143）、エンジンが前分割の前に 1 つに読む。Gemma 3 は 6,408 個（書式のトークン 2 つを含む）で、options の JSON は 103,605 バイト。U+2581 の並びの special は、語彙が空白でつづった語片として引く（エンジンの `cut()`）。
- **語彙の外の追加のトークン**（Gemma 3 の `<image_soft_token>`、id 262,144）は、モデルに行が無いので落とす（`with_a_row()`）。予定に無かった違い: 今までは「The tokenizer has 262145 pieces, but the model has a vocabulary of 262144.」で断っていた。tokenizer.json 自身の語彙が入るときだけ。

## 段取り: model の自分のファイルが在るとき

- **ダミーの空白を持つ形（`Prepend`: Llama・Mistral の系統）の tokenizer.json は、ほかの候補の後に回す。** `tokenizer.model`・`spiece.model` が在って読めればそれを読む（今までどおり）。無いか読めなければ tokenizer.json を読む（CAT-Translate 7B）。訳: 特殊トークンの後の文にダミーの空白を置くかは tokenizer_config.json の `legacy` が決め（T308）、古い transformers が書いた tokenizer.json は `legacy` に依らず全部の文の前に置く。一覧のこの系統は model のファイルの道で本物と合わせてある。
- **ダミーの空白を持たない形（Gemma）は、その場で tokenizer.json を読む。** `legacy` の問いが無い。model のファイルの道は今も `add_dummy_prefix` を読まず、頭に空白を置いてしまう。
- 頼むファイルの列は変わらない（tokenizer.json は今も最初に頼まれ、今までは断られて次へ進んでいた）。

## GGUF の語彙（寄せなかった訳）

`unsloth/gemma-3-270m-it-GGUF` @`c90975dbd40c0c7b275fefaae758c3415c906238` の Q8_0 の頭 24 MiB を読んだ。

- `tokenizer.ggml.model` は `llama`、点数は model のもの（ふつうの語片 255,474 個は全部違う整数）、型は NORMAL 255,474・CONTROL 6,251（`<unusedN>` も）・USER_DEFINED 163（改行・空白・タブの並び、HTML のタグ、`[multimodal]`）・BYTE 256。`add_space_prefix` は false。U+2581 の並びは空白でつづってある。user-defined と control の点数は −1000。
- **今の `sentencepiece_bpe()` は断る**（`add_space_prefix` が false）。`"never"` ができたので prefix は読めるが、それだけでは合わない: 試しに「model の点数・`"never"`・control を special に」で読むと、113,681 文のうち 22,840 文が tokenizer.json の読みと違う（user-defined の空白の並びが −1000 で、`▁world` が先にできる）。user-defined の点数をいちばん上にすると 846 文（U+2581 そのもの、HTML のタグ、`[multimodal]`、special の名前を書いた文）。user-defined を special として先に切ると 9,789 文（空白でつづってあるので、ふつうの空白の並びまで切る）。
- 同じ関数には寄せていない。出どころが違う（merges の順位と、model の点数と型）。GGUF だけで Gemma を開くなら、user-defined を「空白類の並びは点数をいちばん上に、ほかは先に切る」と分ける読みが要る（未実装。一覧の項目は語彙を原本から取るので要らない）。

## CAT-Translate 7B を一覧に足すには（調べだけ）

- 形は Mistral 7B（`model_type: mistral`、hidden 4096、32 層、head 32・KV 8、語彙 61,765、分類器は別、theta 1e6、`sliding_window` null）。`check_config()` は Llama として通す。重みは safetensors のシャード（bfloat16）。
- GGUF: `mradermacher/CAT-Translate-7b-GGUF` に Q8_0（7,955,662,016 バイト: T248 の調べ）。未確認: `gguf_check.py tensors`（CI: 原本 15 GB と GGUF 8 GB）。
- トークナイザはこの回で読める（語彙は原本の tokenizer.json から: `vocabulary: { …, tokenizer: "tokenizer.json" }`）。書式は変換器が読む（上の表。system の文「You are a helpful assistant.」を本物どおり書く）。
- int8 は約 7.5 GB で 64 ビットのメモリ（Chrome と Firefox）。手元では回せない。翻訳のモデルなので、プロンプトの形（0.8B・1.4B の項目の書式）と合わせるかを、足す子タスクで決める。
