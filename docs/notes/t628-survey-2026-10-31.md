## 補足
- **写しの一覧（JS ↔ Python の同じ事実）**: `architectures.ts` ↔ `LAYOUTS`、`folder.ts` の `TOKENIZERS` ↔ `conduct.py`、`madeup.ts` ↔ `forward_plan()`、`BLOCK_TYPES`・塊のバイト数 ↔ `BLOCKS`、`kept.ts` の dtype 名・`models/memory.ts` の比 ↔ `DTYPES`、`IQ_WORDS`・`CODEBOOK_BYTES` ↔ `grids.py`、`CONVERTER`（Python 側の版の持ち主が無い）。今はどれも検査（`plan-keys-check`・`worker-fetches-check`・`kernel-registry-check`・`kept-check`）が突き合わせている。ビルドで Python から JSON を作って TS が `import`（Vite は JSON を束ねられる）すれば、写しと突き合わせの検査が消え、実行時の代償は無い。必要なもの: `make python` の隣に「事実を JSON に書き出す」段 1 つと、Node の試験が同じ JSON を読むこと（`src/` に `.json` の import はまだ無い: 初めての形）。
- 実行時に Python に移せる所はほとんど無い。Pyodide の前に走る所（一覧・見積もり・保存の名前・取得の開始）と Pyodide の無い所（ページ・/benchmark/・GPU の Worker）が大半だから。実行時に移せるのは `worker/conduct.ts` の輪くらい。
- 「ビルド時に Python で作る」は、モデルを狭めず準備完了も遅らせない唯一の形。

## 勧めの順（小さく、安全で、狭めない）
1. `forward/architectures.ts` をビルド時に `LAYOUTS` から作る JSON に（写しと `plan-keys-check` の表の突き合わせが消える）。
2. `folder.ts` の `TOKENIZERS` を `conduct.py` から作る JSON に（極小、門の文は今のまま組む）。
3. 塊の型の番号とバイト数・dtype 名・比（`BLOCK_TYPES`・`kept.ts`・`models/memory.ts`）を `BLOCKS`・`DTYPES` から作る JSON に（`PACKED` の関数は TS のまま）。
4. `CONVERTER` の版を Python の変換器に置き、ビルドで TS へ。
5. `benchmark/madeup.ts` の計画をビルド時に素の Python の `forward_plan()` で作る（手書きの計画が無くなる）。
6. （大）一覧 `src/models/` の項目を Python で書いてビルドで JSON に。得は「なるべく Python」に最も効くが、道具と型の作り直しが大きいので別に採番。
