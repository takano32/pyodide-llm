# T.513 スマホの大きさのモデルを int8・6 ビット・llama.cpp の塊のままで並べる（2026-10-15）

**まとめ**
- **速さはどのモデルでも int8 がいちばん**（CI の arm64 と x86-64 の 4 本、1 トークンもプロンプトも）。6 ビットは int8 の 0.52〜0.74 倍（x86-64 の Gemma 3 1B は 0.96、E2B は 0.91）、塊のまま（Q4_K_M）は 0.76〜0.88 倍（Gemma 3 1B は塊がほとんど残らず 1.0）。CI のランナーでは軽い形ほど速くはならない。
- **軽くなる量**: 6 ビットはメモリが約 2 割減るが取得は変わらない（同じ Q8_0 を取ってブラウザで詰める）。**塊のまま（Q4_K_M）は取得が約 4 割減り**（Shisa 350M 379 → 229 MB、LFM2.5 1.2B JP 1246 → 731 MB）、メモリは 2〜3 割減る。ただし Q4_K_M の中の Q6_K・Q5_K の層（埋め込み・FFN の出・v など）は掛ける部品が無いので int8 に広げる。
- **質の損は小さい**: 1 文字あたりの nats は 6 ビットで −2.8〜+1.0%、Q4_K_M で +0.7〜+6.8%、IQ4_XS で +1.4〜+4.2%（日本語）。12 の問いの事実の当たり（機械で数えた）は形でほとんど動かない。
- **Gemma 3 1B は塊の形でメモリが減らない**（幅 1152 が 256 の倍数でなく、llama.cpp が Q5_0・Q8_0 に逃がしている）が、Q4_K_M の取得は 1069 → 806 MB で速さも質もほぼ int8 のまま。**Gemma 4 E2B は塊の形を作れない**（変換器が Gemma 4 の GGUF を読まない）。E2B を軽くする最大の手は、取得 10.2 GB の safetensors の代わりに GGUF（Q8_0 5.0 GB・Q4_K_M 3.1 GB）を読むこと。
- 持ち主の Android では帯域で決まるなら軽い形が 1.1〜1.4 倍速くなりうるが、計算で決まるなら CI と同じく遅くなる（見込みは両端だけ。端末の一覧へ）。

製品のコードは変えていない。足した道具: `tests/quant_sizes.py`（ファイルの頭だけから形ごとの大きさ）、`tests/quant_combos.sh`（1 つの項目を形ごとに同じランナーで: 大きさ・nats・12 の問い・速さ）、`tests/perplexity_prepare.py --blocks`。

## 測り方

- **形**: int8（今）、int6（`?bits=6` と同じ変換）、塊のまま（`Conversion(blocks=True)`: 項目の `conversion.blocks` と同じ。同じリポジトリの Q4_K_M・IQ4_XS の GGUF を、原本の語彙と config で）。ページが掛けられる塊の型は Saluki の 10 種類で、**Q4_K_M に入っている Q6_K・Q5_K、IQ4_XS の Q5_K・Q6_K、32 個の塊の Q5_0・Q8_0・IQ4_NL には部品が無い**: その型の層が 1 つでもある束は丸ごと int8 に広げる（変換器の今の動き）。
- **取得**: 重みのファイルのバイト（int8 と int6 は項目の Q8_0、塊は GGUF）。**メモリ**: チェックポイント + `footprint()` が文脈 4096 で後ろに置く量（page-27b.mjs の行）。ページのヒープはこれに Pyodide の分が乗る（どの形も同じ）。
- **質**: 富士山の記事（日本語版・英語版）の頭 3000 字を、ページのエンジンで、ページの BOS から 512 トークンの窓で（`start_check.mjs`。日本語の字は T.511.5 と同じ: sha256 `c11a8b19617fef11`、英語 `32d0915ec94035e9`）。1 文字あたりの nats（低いほど良い）と perplexity。12 の問い（`answers.mjs`、項目の書式と標本抽出、greedy と種 1・2、400 トークンまで）は**事実の当たりを機械で数えた**（富士山・3,776・408（日本語と英語）・漱石の本当の作品名・Tokyo の 6 つ × 3 回 = 18。答えの中に語があれば当たり: 読んでいない。T.511.5 の手で数えた数とは比べない）。崩れ（道具の `LOOPS`）はどの形も 0/24。
- **速さ**: `page-27b.mjs speed`（forward.js とソフトウェアスレッド、共有メモリ）。1 トークン（BOS から 64 位置の greedy）を 1 本と 4 本、プロンプト 256 トークンを 16 ずつのブロックで 4 本。形を順に 1 回ずつ、3 ラウンド（順は毎回裏返す）の中央値。1 つの形は 1 つのプロセス（同じプロセスで交互ではない: 同じジョブ・同じ CPU の中の比として読む）。
- **CPU**: arm64 は 1 本の run に全部（Neoverse の 4 論理コア、Node は CPU 名を「unknown」と言う）。x86-64 はモデルごとの run で、AMD EPYC 7763（Shisa 350M・LFM2.5 230M・Qwen3.5 0.8B・LFM2.5 1.2B JP）と EPYC 9V45（Gemma 3 1B・Gemma 4 E2B）: **x86-64 の数はモデルをまたいで比べない**。
- **持ち主の Android の見込み**（式、T.511 と同じ B ≈ 21 GB/s）: 「帯域の端」= 21 GB/s ÷ 1 トークンに読む重み（チェックポイント、E2B は保存に残る表を除いた数）。「計算の端」= int8 の帯域の端 × CI の arm64 の 4 本の比（その形 ÷ int8）。本当の値はこの間か外（どちらで決まるかは端末で測るまで分からない）。

## 勧め（モデルごとの既定の形）

1. **既定の形は int8 のまま**（勧め）。CI では両方の CPU で int8 がいちばん速く、質も同じか良い。6 ビットは今の規則（int8 が入らないときだけ: `weightsFor()`）のままで、データもそれを支える（速さ 0.5〜0.74 倍、軽くなるのはメモリ 2 割だけで取得は同じ）。
2. **取得を減らしたいなら、塊の Q4_K_M を「既定のモデル（Shisa 350M）だけ」に**: 初めての訪問の取得 379 → 229 MB（家の回線で 42〜54 秒 → 25〜33 秒、式）、メモリ 554 → 411 MB。代わりに CI の 1 トークンが 0.88 倍（arm64）・0.79 倍（x86-64）、プロンプト 0.68 倍、日本語 nats +1.2%（事実は 15 → 16、揺れの中）。スマホのユーザが多い（T.511）ので、速さより最初の待ちを取るならこれ。持ち主の端末で速さが逆になる（帯域の端: 53 → 75 tok/s）見込みもある。
3. **Gemma 3 1B の Q4_K_M は取得だけが減る**（1069 → 806 MB、メモリ・速さ・質はほぼ int8）: 取得の減りが純粋な得。ただしスマホの既定の候補でないので急がない。
4. **Gemma 4 E2B**: 塊は無理。軽くする手は (a) 変換器に Gemma 4 の GGUF を読ませる（取得 10.2 → 5.0 GB の Q8_0、表の型 Q5_K を読めれば 3.1 GB の Q4_K_M）、(b) 6 ビット（メモリ約 2.57 → 2.0 GB の見込み、速さ arm64 0.74 倍、質は同じか良い）。どちらも「desktop only」の線（約 1.85 GB）は越えたまま。
5. 塊の形をもっと軽くするには **Q6_K と Q5_K の部品**（埋め込み・w2・v が広がらなくなる）。足したときの大きさと速さは未計測（新しいタスクにするかは持ち主: 下の C）。

## 持ち主に聞くもの（勧めを先頭に）

- **A. 既定のモデル（Shisa V2.1c LFM2 350M）の形**
  1. int8 のまま（勧め）: 今の速さ。初めての取得は 379 MB。
  2. Q4_K_M の塊のまま: 初めての取得 229 MB（約 4 割減）・メモリ約 26% 減。CI の速さは 0.79〜0.88 倍、nats +1.2%。持ち主の Android で速くなるか遅くなるかは端末で測るまで分からない。
  3. int8 のまま、持ち主の Android で Q4_K_M と int8 を測ってから決める（端末の一覧に積む）。
- **B. Gemma 4 E2B を軽くする手**
  1. 変換器に Gemma 4 の GGUF（Q8_0）を読ませるタスクを積む（勧め）: 取得 10.2 → 5.0 GB。メモリは int8 のまま。
  2. 6 ビットを E2B の既定にする: メモリ約 2.0 GB、取得は 10.2 GB のまま、速さ 0.74〜0.91 倍。
  3. 何もしない。
- **C. Q6_K・Q5_K の部品を足すか**
  1. 今は足さない（勧め）: CI では塊の形は int8 より速くならず、得は取得とメモリだけ。A で 2 を選んだときに見直す。
  2. 足す: Q4_K_M の埋め込み・w2・v も塊のまま（メモリがさらに減る。量は未計測）。

## CI の判断

CI を回した（6 本）。訳: GB 級のモデル（E2B）と速さの判断は手元で見られない。x86-64 はモデルごとに 5 本（1 本に問いと速さをまとめた）、arm64 は速さだけを 1 本に全部。手元では道具を LFM2.5 230M の小さな組で通した。
