# T.584・T.585: 道具を bun でも回す、と bun の手元のビルド（2026-10-25）

## 持ち主の決め

- **手元だけ bun**（2026-10-25、持ち主が選択肢で）: 手元の道具と軽い組を bun でも回せるようにする。CI とデプロイは Node 24 のまま（方針 3 は変えない）。
- **bun の未対応を見つけたら上流に PR を出すのが目標**（同じ日、持ち主）。
- **bun を手元で建てるときは、なるべく新しいものを入れない**（同じ日、持ち主「なるべく新しいものが入らないように考慮しつつ進めていいです」）。

## 軽い組を bun で回す

```
RUNTIME=bun PATH=$PWD/.venv/bin:$PATH bash tests/suite.sh light
```

手元（a1-free、bun 1.4.4）で 411 秒で通った。bun で回せない 2 本は `tests/suite.sh` の `BUN_LEAVES` が外し、外した訳を 1 行出す。

| 外した試験 | 訳 |
|---|---|
| `tests/memory-check.mjs` | bun の WebAssembly のメモリの `grow` が、エンジンの形では中身を写し直すらしく 1 回に約 1 秒かかる（1.8 GB のモデル。Node は在るまま伸ばす）。27B の層 4 つの作り物 1 つのエンジンが Node 0.4 秒・bun 16〜20 秒で、全体は 30 分の上限を越える |
| `tests/blocks-forward-check.mjs` | bun は 64 ビットの WebAssembly のメモリを既定で切っている（`BUN_JSC_useWasmMemory64=1` で入る）。入れても `new WebAssembly.Memory({ address: "i64" })` の `address` を読まず 32 ビットのメモリになり、64 ビットのカーネルの import が断られる |

bun で回すために直したもの（どれも Node でも同じに動く）:

- `tests/untyped.mjs`: 型を消す `node:module` の `stripTypeScriptTypes` が bun に無い → npm の `amaro`（Node の型の消し方の元）を使う。`src/` の 125 ファイルで Node と同じ長さ・同じ文（違いは消した型の中の空白の字 1 つ: Node は U+00A0、amaro は空白）。
- `tests/fresh.mjs`: 部品をまっさらに読み直す試験（`page-parts-check`・`worker-parts-check`・`worker-outdated-check`）は Node では URL の問い（`?case=N`）で別のモジュールを作っていた。bun は問いが違っても同じモジュールを返すので、bun では隣に写しを作って読み、読んだらすぐ消す。
- `tests/bun-preload.mjs`（`bunfig.toml` の `preload`）: bun はメインのスレッドで `onmessage` を置くとプロセスを終えない。試験は worker のモジュール（`worker.ts`・`gpu.ts`・ベンチの Worker）を読み、それが `onmessage` を置くので、「ok」と出たまま終わらなかった。メインのスレッドでだけ `onmessage` をふつうの欄にする。
- `tests/limited.mjs`: bun は Node の報告の旗（`--report-on-signal` など）を受けないので、bun では付けない（期限はそのまま）。
- `tests/bundle.mjs`: `readdirSync` の順が bun では違う → 名前を並べてから使う。
- `tests/gpu-check-parts-check.mjs`: (1) JavaScriptCore の `Math.exp`・`Math.log` は V8 と最後の 1 ビットが違う → 0 との比べを 1e-15 までに。(2) bun の `--check` はファイルを走らせる → 構文の確かめは `@babel/parser` で。

## bun の違い（上流に出す候補: T.585）

| 違い | 上流 | 見通し |
|---|---|---|
| `node:module` に `stripTypeScriptTypes` が無い | issue #39971、PR #41649・#35517 が開いている | 出さない（もう出ている） |
| メインのスレッドで `onmessage` を置くとプロセスが終わらない | issue #24256、PR #32482 など | 出さない（もう出ている） |
| 動的 import で、問い（`?case=1` と `?case=2`）だけ違う URL が同じモジュールになる | 見当たらない | 候補。仕様（モジュールの表は URL 全体が鍵）と Node は別のモジュール |
| WebAssembly のメモリの `grow` が、エンジンの形（カーネルのインスタンスが import した、書き込み済みの 1.8 GB）で写し直すらしく 1 回に約 1 秒 | 見当たらない | 候補。小さな再現をまだ作れていない（1 GiB を書いてインスタンスに import させただけでは速い） |
| 64 ビットのメモリ（`useWasmMemory64`）を既定で切っていて、入れても `WebAssembly.Memory` の `address: "i64"` を読まない | 切っているのは bun の決め（`src/jsc/bindings/ZigGlobalObject.cpp`: 上流が安定するまで） | `address` の欄は候補（JS API の今の仕様の名前） |

## bun の手元のビルド（試して、やめた）

**結果（2026-10-25）: 建たない、手元では建てない（持ち主の決め）。** 下の形で `bun run build:debug` を回すと 28 秒で止まった: 「clang is LLVM 22.1.2 and rustc's LLVM is 23.1.1; they have to be the same major version」（リンクは両方のコンパイラの LLVM のビットコードを読む）。手元の Rust は stable 1.99.1 も LLVM 23.1.1 なので、LLVM 22 ではどの Rust でも建たない。建てるには LLVM 23 を入れる（apt.llvm.org を sudo で）が、持ち主はやめると決めた。**取りまとめ役の誤り**: ビルドの道具は `RUSTUP_TOOLCHAIN=stable` を付けても自分で rustup を呼び、固定の nightly（588 MB）を `~/.rustup` に入れた。持ち主の決めで `rustup toolchain uninstall` で消し、ビルドが bun のフォルダに作った `build/` も消した（`~/.bun/build-cache` はできていない）。次に試すなら、Rust の置き場は `BUN_TOOLCHAIN_RUST`（sysroot）で名指す（rustup に任せない）。

以下は試した形の記録。

- 置き場: `~/GitHub/bun`（`origin` = `git@github.com:oven-sh/bun.git`、`my` = フォーク `git@github.com:takano32/bun.git`、どちらも ssh）。
- 使うもの（今ある物だけ）: Rust は rustup の stable 1.99.1（`~/.rustup`）、LLVM は apt の 22（`/usr/lib/llvm-22`: clang-22・ld.lld 22.1.2）、cmake・ninja・go・ruby、bun 1.4.4。
- 環境変数（この 3 つだけ）:

| 環境変数 | 値 | 訳 |
|---|---|---|
| `RUSTUP_TOOLCHAIN` | `stable` | リポジトリの `rust-toolchain.toml` は `nightly-2026-09-15` を指定していて、そのままだと rustup が nightly を取りにいく |
| `RUSTC_BOOTSTRAP` | `1` | bun の Rust は nightly の機能を使う（`#![feature(...)]` が 26 の crate に、核の `bun_core`・`bun_alloc`・`jsc`・`runtime` も）。stable は `#![feature]` を断る（E0554）が、この変数で受け付ける（同じコンパイラで、門だけが違う）。stable 1.99 は固定の nightly より数週間古いので、作りかけの機能（`generic_const_exprs`・`adt_const_params`）の形が違えば通らない（未確認） |
| `BUN_TOOLCHAIN_LLVM` | `/usr/lib/llvm-22` | ビルドは LLVM 23.1.1 を求めるが、この変数で置き場を名指すと版の確かめを外す。作り済みの WebKit は LLVM 23 で作られていて、LTO（release）はそのビットコードを読めないので debug のビルドで（`bun run build:debug`）。CONTRIBUTING.md は版の違いで実行時のメモリ確保が壊れうると書く |

- キャッシュはホームの今ある置き場を使う（指定しない）: crates は `~/.cargo/registry`（598 MB、ある物は取り直さない）、bun の install は `~/.bun/install/cache`。bun のビルドのキャッシュ `~/.bun/build-cache` は新しくできる（既定の置き場: `BUN_BUILD_CACHE_DIR` で変えられる）。
- 機械: 2 コア・メモリ 11 GB・空き 61 GB。最初のビルドは数時間の見込み（未計測）。
