## 結論（先に）

- **27B は 16 GiB の 64 ビットのメモリに入る**。重みは PTQ1_0 で 5.53 GiB、文脈 4096 なら状態と KV を足して 5.92 GiB。Safari（4 GiB）には入らない。
- **CPU の速さの見積もりは約 1〜1.7 tok/s**（持ち主の Android、4 本。式は 6 節。未計測）。1 トークンに 25.6 G の積和が要るため。カードは考える形（既定）に出力 16384 トークンを勧めていて、1 tok/s では 4.5 時間になる。
- **足すものは台帳の見込みより 1 つ多い**: 重みは「回した基底」で入っていて、行列を掛ける前に毎回、活性値に符号と Walsh–Hadamard 変換を掛けなければならない（F16 のファイルも同じ）。
- **小さい実物が 2 つある**: 同じ hybrid attention の Qwen3.5 0.8B（Q8_0 の GGUF 812 MB、3 値でない）と、3 値の Ternary-Bonsai-1.7B（PQ2_0 463 MB、形は今ある Qwen3）。
- **勧め: 小さいモデルから**。hybrid attention は Qwen3.5 0.8B で、3 値は Ternary-Bonsai-1.7B で先に通し、それから 27B。順と持ち主に決めてもらうことは 7 節。

## 1. Qwen3.8 の hybrid attention

### 種類と層の並び

- linear attention は **Gated DeltaNet**。transformers のクラスは `Qwen3_5GatedDeltaNet`（TF `src/transformers/models/qwen3_5/modeling_qwen3_5.py` 503〜662 行）、llama.cpp では `llm_build_delta_net_base`（FORK `src/models/delta-net-base.cpp`）と `GGML_OP_GATED_DELTA_NET`。
- Qwen3.8 は Qwen3.5 と同じアーキテクチャ。Q38 の config.json は `model_type: qwen3_5`、GGUF は `general.architecture = qwen35`。
- **64 層のうち 4 層ごとの 4 つ目が full attention**（層 3・7・…・63 の 16 層）、残り 48 層が linear attention。config の `layer_types` と `full_attention_interval: 4`、GGUF の `qwen35.full_attention_interval = 4`。FORK `src/models/qwen35.cpp` 21〜27 行は `(i + 1) % 4 != 0` の層を再帰の層と読む。
- 層の外側はどちらの層も同じ（TF 860〜913 行）: `x += mixer(norm(x))`、`x += mlp(norm(x))`。

### linear attention の層の計算（1 トークン）

出どころは TF 437〜496 行（`torch_recurrent_gated_delta_rule`）と 549〜662 行、FORK `src/models/qwen35.cpp` 408〜588 行、`src/models/delta-net-base.cpp` 289〜371 行。x は層の norm の後の活性値（5120）。

1. `qkv = W_qkv x`（10240 = q 2048 + k 2048 + v 6144）、`z = W_z x`（6144）、`b = W_b x`（48）、`a = W_a x`（48）。
2. **畳み込み**: qkv の 10240 チャネルそれぞれに、長さ 4 の因果の 1 次元の畳み込み（チャネルごと、bias なし）。今のトークンと前の 3 トークンの qkv を掛けて足す。その後 SiLU。
3. q と k を head（128）ごとに L2 で正規化（`x * rsqrt(sum(x²) + 1e-6)`）。q は 1/√128 倍。k の head は 16、v の head は 48 なので、q と k は 3 つの v の head に同じものを使う。
4. `beta = sigmoid(b)`、`g = −exp(A_log) × softplus(a + dt_bias)`（v の head ごとに 1 つずつ）。
5. v の head ごとに、状態 S（128 × 128）を更新する: `S ← S × exp(g)`、`kv = S の k 方向の和（S·k）`、`delta = (v − kv) × beta`、`S ← S + k ⊗ delta`、出力 `o = S·q`（128）。
6. `o` を head（128）ごとに RMSNorm（重み 128 個）して `SiLU(z)` を掛ける（`Qwen3_5RMSNormGated`、TF 217〜233 行）。
7. `W_out`（5120 × 6144）を掛ける。

**状態**: linear attention の層は KV キャッシュを持たず、代わりに次の 2 つを持つ。どちらも文脈の長さに依らない。

- 再帰の状態: v の head 48 × 128 × 128 の float32 = 786,432 個 = 3.0 MiB / 層。48 層で **144.0 MiB**。
- 畳み込みの状態: 前の 3 トークンの qkv = 3 × 10240 個 / 層。48 層で 5.6 MiB。

プロンプトのまとめ処理は、transformers では 64 トークンずつの塊の式（`torch_chunk_gated_delta_rule`、TF 300〜435 行）、llama.cpp では 1 つの演算の中でトークンを順に回す形（FORK `ggml/src/ggml-cpu/ops.cpp` 10941〜11155 行）。1 トークンずつの式を順に回しても同じ結果になるはず（確かめるのは T229）。

### full attention の層の計算

出どころは TF 748〜820 行、FORK `src/models/qwen35.cpp` 327〜406 行。今の Qwen3（T124）との違いは 3 つ。

- **q の行列は 2 倍の幅**（5120 → 12288 = 24 head × 256 × 2）。head ごとに前の 256 が q、後ろの 256 が gate。attention の出力（6144）に `sigmoid(gate)` を掛けてから o（6144 → 5120）を掛ける。
- **RoPE は head の先頭 64 次元だけ**（0.25 × 256）。theta は 1e7。テキストだけなら 3 つの軸の位置が同じなので、普通の RoPE と同じになる（TF 1262〜1264 行と 1450 行が位置を 3 軸に同じ値で広げ、203〜212 行が軸ごとの値を入れ替える）。回す 64 次元の中の並びは HF の rotate_half（前の 32 と後ろの 32 が対）。GGUF の q と k がどちらの並びかは未確認（Qwen3 の GGUF は HF の並びのまま、T203）。
- head ごとの q と k の RMSNorm（重み 256 個、今ある `qk_norm` と同じ）、GQA（24 対 4）、bias なし。

KV: 1 位置に 16 層 × (K + V) × 4 head × 256 = **32,768 個**。float16 で 65,536 バイト（DEMO `KV-CACHE.md` の「64 KiB per token」と合う）、float32 で 131,072 バイト。

### norm・MLP

- RMSNorm（eps 1e-6）。**HF の重みは 0 を中心に持ち `1 + weight` を掛ける**（TF 840〜854 行）。GGUF は足した後の値で入っている（FORK `conversion/qwen.py` 394〜395 行が `linear_attn.norm.weight` 以外の norm に 1 を足す）。
- MLP は SwiGLU: `down(silu(gate(x)) × up(x))`、5120 → 17408 → 5120、bias なし（TF 823〜836 行）。

## 2. トークナイザと書式

出どころは Q38 の `tokenizer.json`・`tokenizer_config.json`・`chat_template.jinja`・`generation_config.json` と、B2 の GGUF のメタデータ。

- byte-level BPE。語彙 248,044 語 + 追加のトークン 33 個（248044〜248076）。`vocab_size` は 248320 で、GGUF の `tokenizer.ggml.tokens` も 248320 個（残りは詰め物のはず、中身は未確認）。merges 247,587 個。1 バイトの語片は 256 個とも語彙にある。
- 正規化は NFC。**前分割の正規表現は今のエンジンに無い形**: `(?i:'s|'t|'re|'ve|'m|'ll|'d)|[^\r\n\p{L}\p{N}]?[\p{L}\p{M}]+|\p{N}| ?[^\s\p{L}\p{M}\p{N}]+[\r\n]*|\s*[\r\n]+|\s+(?!\S)|\s+`。今の `qwen` の型との違いは結合文字（`\p{M}`）を字の並びに入れること。GGUF は `tokenizer.ggml.pre = qwen35`。`llama2_convert.py` の表（1756 行）と `GGUF_PRETOKENIZERS` に 1 つずつ足すことになる。
- `add_bos_token: false`、tokenizer_config の `bos_token` は null。config の `bos_token_id` は 248044（`<|endoftext|>`）で eos と同じ。本物の使い方は BOS を置かない。ページはどのモデルでも BOS から始める（T131）ので、ここは T233 で本物と比べる。
- 止まりのトークン: 248046（`<|im_end|>`）と 248044（`<|endoftext|>`）。
- 特殊トークン: `<|im_start|>` 248045、`<|im_end|>` 248046、視覚の `<|vision_start|>` など。special でない追加のトークンは `<tool_call>` 248058、`</tool_call>` 248059、`<tool_response>`、`</tool_response>`、`<think>` 248068、`</think>` 248069、`<|fim_*|>`、`<|repo_name|>`、`<|file_sep|>`。T143 の決まりどおり変換器が specials に入れる形で足りる。
- Qwen3.5 0.8B の tokenizer.json は語彙・merges・前分割・正規化が Qwen3.8 と同じ。違いは追加のトークン 7 個（音声の `<|audio_*|>` と `<tts_*>`）だけ。

### chat_template（8952 字、ChatML）

- **マクロ（`render_content`）を呼ぶので、T127 の読み手は読めない**。llm-jp-4 と同じく一覧に手で書く。
- 考える形（既定）: `enable_thinking` を言わないか真なら、`reasoning_effort` の既定は `xhigh` で、**システム文が無くてもシステムのターンが入る**。

  ```
  <|im_start|>system\nReasoning effort is set to xhigh. Please think carefully through the task, validate key assumptions, consider plausible alternatives, and prioritize correctness, consistency, and clarity in the final answer.<|im_end|>\n<|im_start|>user\n{prompt:trim}<|im_end|>\n<|im_start|>assistant\n<think>\n
  ```

- `reasoning_effort: medium` ではシステムのターンが無く、`<|im_start|>user\n{prompt:trim}<|im_end|>\n<|im_start|>assistant\n<think>\n`。`low` は別の文のシステムのターン。`high` は断られる（B2 `KNOWN_ISSUES.md`）。
- すぐ答える形（`enable_thinking: false`）: システムのターンは無く、終わりが `<|im_start|>assistant\n<think>\n\n</think>\n\n`。今の Qwen3 の 2 つの形（T124）と同じ作り。
- 勧められている生成の設定（B2 のカード）: 考える形は temperature 1.0・top_p 0.95・top_k 20・min_p 0.05、すぐ答える形は temperature 0.7・top_p 0.80・top_k 20・presence_penalty 1.5。**エンジンには top_k と min_p と presence_penalty が無い**（あるのは temperature・top-p・繰り返しの罰）。

## 3. PTQ1_0 と PQ2_0 のブロック

### 型の番号と定義

- `GGML_TYPE_PQ2_0 = 142`、`GGML_TYPE_PTQ1_0 = 143`（FORK `ggml/include/ggml.h` 433〜436 行）。ファイルの種類の番号は PQ2_0 が 141、PTQ1_0 が 143（FORK `include/llama.h` 159〜161 行。実物の `general.file_type` もそう）。
- 構造体は FORK `ggml/src/ggml-common.h` 199〜220 行。どちらも **128 個の重みに float16 のスケールが 1 つ**。

| 型 | 1 ブロックのバイト | 並び | ビット / 重み |
|---|---|---|---|
| PQ2_0 | 34 | `d`（float16 のスケール、2 バイト）、`qs[32]`（2 ビット × 128） | 2.125 |
| PTQ1_0 | 28 | `qs[24]`（1 バイトに 3 値 5 個、120 個ぶん）、`qh[2]`（1 バイトに 3 値 4 個、8 個ぶん）、`d`（float16 のスケール、2 バイト） | 1.75 |

- グループは行（1 つの出力）の中の、入力の向きに続く 128 個。行の幅は 128 の倍数でなければならない（5120・6144・17408・1024 はどれも 128 の倍数）。

### CPU の参照の広げ（自分の言葉で）

**PQ2_0**（FORK `ggml/src/ggml-quants.c` 494〜511 行、`dequantize_row_pq2_0`）: j 番目の重みは `qs[j / 4]` の下から `(j % 4) × 2` ビット目の 2 ビット q で、値は `(q − 1) × d`。q の 0・1・2 が −1・0・+1。q = 3 は +2 になるが、3 値のファイルでは使われない（下の確かめで 0 個）。

**PTQ1_0**（同 2196〜2285 行、`dequantize_row_ptq1_0`。upstream の TQ1_0 と同じ 3 進の詰め方を 128 個のグループにしたもの）:

- 1 バイトから n 番目（0〜4）の 3 値を取る式: `q = (バイト × 3^n) の下 8 ビット`、`xi = (q × 3) >> 8`（0・1・2）、値は `(xi − 1) × d`。詰めるときは 5 個の 3 値を 3 進の数（0〜242）にして `ceil(数 × 256 / 243)` を 1 バイトに置く。
- **重みの順はバイトの順ではない**。`qs` を 16 バイトの塊と 8 バイトの塊に分け（段の大きさ 32・16・8 のうち 24 バイトに入るもの）、塊ごとに「n を外、バイトを内」に回す。重み 0〜15 は `qs[0..15]` の 0 番目の 3 値、16〜31 は同じバイトの 1 番目、…、64〜79 は 4 番目。重み 80〜87 は `qs[16..23]` の 0 番目、…、112〜119 は 4 番目。重み 120・121 は `qh[0]`・`qh[1]` の 0 番目、…、126・127 は 3 番目（`qh` は 4 個の 3 値を上の桁に寄せて詰めてある）。

**確かめ**（`.tmp/t228/sample.py`）: 上の読み方で `blk.0.attn_gate.weight` の 64 行・`token_embd.weight` の 64 行・`blk.3.attn_q.weight` の 32 行を PTQ1_0 と PQ2_0 から広げ、F16 のファイルの同じ所と比べた。**3 つとも全部の値がビット単位で同じ**（差の最大 0）。PQ2_0 の q = 3 は 0 個。−1・0・+1 はほぼ 3 分の 1 ずつ（例: 109,922・107,419・110,339）。スケールは 0.005〜0.03 の桁。

### どのテンソルがどの型か（B2 の GGUF の頭から）

| 型 | 個数 | 値の数 | 中身 |
|---|---:|---:|---|

テンソルのデータは PTQ1_0 で 5,935,527,936 バイト（5.528 GiB）、PQ2_0 で 7,195,047,936 バイト（6.701 GiB）。頭（メタデータと表）はどちらも 11,120,992 バイト。

### 回した基底（Hadamard）: 台帳に無かったもの

**3 値の行列はそのままでは掛けられない**。重みは回した基底で入っていて、掛ける前に活性値を同じように回す。F16 のファイルも同じ基底（B2 `KNOWN_ISSUES.md`:「F16 は素の llama.cpp で読めるが、壊れた文を出す」）。

- メタデータ（B2 の GGUF）: `prism.hadamard.version = 1`、`block_size = 1024`、`transform = normalized-sylvester-walsh-hadamard`、`axis = input-last-dimension`、`sign_mode = explicit`、`sign_widths = [5120, 6144, 17408]`、`sign_values`（±1 が 28,672 個 = 5120 + 6144 + 17408）、`weight_names`（401 個 = 3 値のテンソルから `token_embd.weight` を除いた全部）、`inverse_weight_names = [token_embd.weight]`、`gdn_v_grouped = true`。
- **行列の前**（FORK `src/llama-graph.cpp` 1546〜1576 行 `build_lora_mm`、白書 2.4 節の `f(x) = W(Rx)`、`R = H S / √1024`）: 入力 x に、幅ごとの符号（±1）を掛け、1024 個ずつの塊に Walsh–Hadamard 変換（1/√1024 倍）を掛けてから、3 値の行列を掛ける。同じ入力を使う行列（qkv と gate、ffn の gate と up、q・k・v）は 1 回の変換を使い回す。
- **埋め込みの後**（同 2398〜2410 行 `build_embd_rows`）: 引いた行 z に Walsh–Hadamard 変換を掛けてから符号を掛ける（`h = s × (H z)`）。
- **`ssm_out` の前だけ**（FORK `src/llama-model.cpp` 2123〜2131 行と `llama-graph.cpp` 1561〜1568 行）: 活性値の v の head を GGUF の並びから HF の並びに戻してから符号と変換。
- 変換そのもの（FORK `ggml/src/ggml-cpu/ops.cpp` 12066〜12140 行）: 1/√n を掛け、幅 1・2・4・…・512 の順に「和と差」の蝶を回す。行列で書くと、行と列の番号の AND の 1 のビットが奇数個なら −1/√n、偶数個なら +1/√n（FORK `src/llama-model.cpp` 2054〜2065 行）。
- 1 トークンの変換の量: 層ごとに 33 塊（5 + 6 + 5 + 17）、全体で 2,122 塊、足し引き約 2,170 万回。3 値の積和（25.6 G）の 0.1% で、CPU では無視できる。白書（DEMO `bonsai-2-27b-whitepaper.pdf` の付録 A.2）は、GPU ではディスパッチの数として大きいと書いている。
- 自分で作った PQ2_0 や PTQ1_0 は動かない（回した重みでないため。B2 `KNOWN_ISSUES.md`）。

### CPU の掛け算のカーネル（fork）

- fork の CPU は、活性値を Q8_0（32 個ごとに float16 のスケール、int8 の値）に量子化し、3 値のグループ 128 個を 4 つの Q8_0 のブロックと整数で掛ける（FORK `ggml/src/ggml-cpu/quants.c` 233〜279 行が PQ2_0、281〜345 行が PTQ1_0。PTQ1_0 は 1 グループを int8 の 128 個に広げてから掛ける）。ARM NEON の PQ2_0 は 2 ビットを表引きとシフトで int8 に広げて `sdot`（FORK `ggml/src/ggml-cpu/arch/arm/quants.c` 297〜361 行）。x86 には PQ2_0（`arch/x86/quants.c` 601 行から）と PTQ1_0（同 717〜791 行: SSE2 か SSSE3 で、バイトに 3 を掛けては上のバイトを取る形で 16 個ずつ 3 値を取り出し、Q8_0 の活性値と掛ける）がある。**ARM NEON の PTQ1_0 のカーネルは、この版には無い**（`arch/arm/quants.c` に `ptq1_0` の字が無く、広げてから掛ける generic に落ちる）。WASM のカーネル（`arch/wasm/quants.c`）には 2 つの型とも無い。B2 `KNOWN_ISSUES.md` は「x86 の速い PTQ1_0 は PR #250 でレビュー中」と書いている。
- これは今のエンジンの int8 の道（重みは int8、活性値は 7〜8 ビット、`relaxed_dot`）とほぼ同じ形。T98 の 6 ビット（グループを int8 に広げて掛ける）がそのまま手本になる。

### 速さの見積もり（どれも未計測。式と、もとにした記録）

1 トークンが読む 3 値の重みは 25,598,361,600 個（全部の 3 値から、行を 1 つ引くだけの埋め込みを除いたもの）。読むバイトは PTQ1_0 で 5.66 GB、PQ2_0 で 6.86 GB。

- **帯域の上限**: tok/s ≤ 読みの速さ ÷ 1 トークンのバイト。
  - 持ち主の Android の CPU 4 本（27.6〜28.7 GB/s、T158）: PTQ1_0 4.9〜5.1、PQ2_0 4.0〜4.2 tok/s。
  - 持ち主の Android の GPU（39.9 GB/s、T151）: PTQ1_0 7.1、PQ2_0 5.8 tok/s。
  - a1-free の 1 本（11.1〜11.8 GB/s、T163）: 2.0〜2.1、1.6〜1.7 tok/s。
- **計算の上限**: tok/s ≤ 積和の速さ ÷ 25.6 G。3 値を int8 に広げて今の int8 のカーネルと同じ命令で掛けるなら、積和の速さは int8 のカーネルを越えない。
  - 持ち主の Android の 4 本: 1 トークンの int8 は 27.6〜28.7 G 積和/秒（1 バイト 1 積和）、プロンプトのタイルは 30.8〜43.9（T158）→ **1.1〜1.7 tok/s**。
  - a1-free の 1 本: 「relaxed_dot と 2 つの読み」の上限 33.1〜33.5 G 積和/秒（T163）→ 1.3 tok/s。
  - CI の x86-64 の 4 本: Qwen2.5 7B の int8（7.6 GB）が 3.5 tok/s（T101）= 26.6 G 積和/秒 → **1.0 tok/s**。
- **だから 27B の CPU は計算で決まり、見積もりは約 1〜1.7 tok/s**。帯域には 3〜4 倍の余りがある。広げの手間（6 ビットでは 1 本で int8 の約 0.45 倍だった、T98。T166 で 1.26〜1.64 倍に戻した）のぶん、これより遅くなりうる。int8 に広げずに 3 値のまま表引きで足す形（BitNet の TL1・TL2）が V8 で速いかは未計測。
- GPU（T232）は帯域の上限まで 5.8〜7.1 tok/s の余地があるが、3 値のシェーダの速さは未計測。
- **考える形の重さ**: カードは出力の上限 16384 トークンを勧める。1 tok/s なら 16384 秒（約 4.5 時間）、256 トークンの答えでも 4 分強。すぐ答える形（`<think>\n\n</think>\n\n`）を既定にしないと、CPU では答えまで届かない。
- fork の実測（B2 のカード、参考）: M5 Pro の Metal で PQ2_0 が 28.1 tok/s（重みの読み 204 GB/s）、L4 で 29.8。CPU だけの 27B の数字はカードにも DEMO の `community-benchmarks/bonsai2/` にも無い。

### 持ち主に決めてもらうこと

- **27B を最後まで進めるか**。CPU の見積もりは約 1 tok/s で、GPU の見込みは未計測。小さいモデル 2 つ（上の 1 と 2）は 27B をやめても残る成果になる。
- 小さいモデル（Ternary-Bonsai-1.7B、Qwen3.5 0.8B）を一覧に足してよいか。
- 27B の詰め方: PTQ1_0（5.53 GiB、広げが重い）か PQ2_0（6.70 GiB、広げが軽い）か。メモリのきついスマホを的にするなら PTQ1_0。
