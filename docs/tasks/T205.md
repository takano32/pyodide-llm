### T205 [バグ][計測実行] iPhone でベンチのモデルの節が落ちる — 状態: **完了（本線に入れた 250c103。レビュー済み。本当の原因は T214 で直した）**
- 起きたこと: 持ち主の iPhone（Safari）で `/benchmark/` のモデルの節（ラウンド「everything」）がタブごと落ちる。
- 調べ（見積もりで、実機では未計測）: 今日 2 段でメモリが増えた。T176 で既定のモデルを llm-jp-3 150M にした（節の合計が約 0.3 → 0.5 GB）。T152 で生成も GPU に置いた（GPU の置き場が 73 → 189 MB: 分類器 57.4 MB と埋め込み 57.4 MB が増えた）。**ラウンドの読み込みが前の GPU の後始末を待たずに始まる**: `forward.js` の `release()` の中の `stopGpu()` は `{type:"stop"}` を送るだけで、`gpu.js` の `end()` が後から `destroy()` と `device.destroy()` をする。そのため GPU の残り（最大 189 MB）とキャッシュからの取得（64 MB）などが重なる。WebKit では WebGPU のバッファも WebContent のプロセスの持ち物に数えられる（T173 の調べ）ので、同じ jetsam の上限に入る。
- **持ち主の判断（2026-09-27）: 案 2 + 案 1**。コミットは 2 つに分け、どちらも 1 つで戻せる形に。
- **案 2（根本の直し）**: GPU の Worker の後始末が終わるのを待ってから次を読む。`gpu.js` の `end()`（止め・`unusable`・準備の途中の止めのどれもここに来る）が `self.close()` の前に `{type:"ended"}` を送り、`forward.js` の `release()` はそれを待つ Promise を返す（Python の `Llama.release()` がそのまま返す）。`worker.js` の `load()` は前のモデルを手放した後にそれを待つ（ベンチのラウンドもモデルのページの切り替えも同じ `load()`）。**最大 5 秒**（`GPU_END_MS`）で、それまでに言わない Worker（コンパイルから戻らない）は `terminate()` して先へ。止めた後に届く「ready」などは無視する（それまでは止めた後の遅い ready が `gpuOn` を立てえた）。準備の途中（`starting`）の止めは、`start()` が次の段で `end()` に来る（段の中の 1 つのコンパイルは最大 180 秒なので、そこで止めれば 5 秒で見切る）。worker.js の「its page path starts the GPU after them」は実際の順（経路の表 → ラウンド）と逆だったので直した。
