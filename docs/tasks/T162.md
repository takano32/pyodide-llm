### T162 [性能][CPU] swiglu と gelu を SIMD に — 状態: **完了（本線に入れた b86c915。小さな直しなので本会話が確かめ、Opus xhigh のレビューは付けない: 持ち主と決めた「重さで分ける」）**
- 根拠: 今はスカラーで、SIMD の形の 4.4 倍遅い。1 トークンの 3〜5% で、スレッドで分けていない（開発機）。
- 作るもの: `vexp` で 4 つずつ。
- 完了条件: float32 のモデルの文が NumPy と同じ（`vexp` と `fexp` は同じ式。違えば線を引く）。
- **作ったもの（2026-09-27）**: `kernels/kernel.ts` の `swiglu` と `gelu` を `vexp` で 4 つずつ（端数は今までのスカラー）。`vexp` に上の切り詰め（88、`fexp` と同じ）を足した: それまで `vexp` は x ≤ 0 だけで使われていた（softmax とサンプリング）が、swiglu の exp(−v) と gelu の exp(−2z) は正にもなる（T158 の `swiglu4` にはこれが無く、v < −88 で指数のビットがあふれる）。`vexp` と `fexp` の違いは −87 より下だけ（`fexp` は 0、`vexp` は exp(−87) = 1.6e-38）で、1 + それは float32 で 1 なので、**swiglu と gelu の結果は前のスカラーとビット単位で同じ**。スレッドには分けていない（作るものに無い）。元ネタは写していない（うちの `fexp` の式を 4 つずつにしただけ）。
- **確かめ**: smoke に「4 つずつ（長さ全部を 1 回）と 1 つずつ（n = 1 で端数の道）がビット単位で同じ」を足した（両方の切り詰めの前後・±200・±3e38・±inf・0 と −0・一様と正規の 8000 個、swiglu と gelu）。わざと壊すと落ちる: `vexp` の 88 の切り詰めを外す → swiglu が落ちる、gelu の v³ の掛ける順を変える → gelu が落ちる。float32 の stories15M と stories42M の greedy の 256 トークンは forward.js と NumPy で同じ文（`.tmp/t162/greedy.mjs`）。pytest 520 件、smoke、forward-check（と `--plain`）、threads-check が通る。
- **速さ**（a1-free の Node、1 本、n = 8192、main のカーネルとこのブランチのカーネルを同じプロセスで交互に 7 回ずつを 3 回、`.tmp/t162/bench.mjs`。**測る前後の load の 1 分平均 0.27〜0.43、5 分平均 0.88〜0.89**）: swiglu は 1 数あたり 13.5 → 3.28 ns（**4.12 倍**）、gelu は 17.6 → 4.14 ns（**4.24 倍**）。3 回とも同じ。1 トークンへの効き（式、未計測）: llm-jp-3 150M の 12 層 × 2048 で 0.33 → 0.08 ms。
