- **持ち主の Android の実測（2026-09-28、Xiaomi 13T Pro の Chrome、スクリーンショット）**: Llama 3.2 3B Instruct が「SIMD kernels, int8, relaxed SIMD, prompts and answers on WebGPU」で答え、250 トークンを 6.0 tok/s（1 回）。答えの文は壊れていない。見積もり（GPU だけで約 5.7 tok/s、CPU で約 7.9 tok/s）と比べると GPU の側は見積もりどおり。CPU に読み直していないのは、ベンチの CPU の節の値が無いか、プロンプトを入れた比べで GPU が勝ったため（どちらかは未確認）。
- 根拠: 今は重みを WebAssembly のメモリと GPU の両方に持つ（1B で約 1.1GB 増える）。スマホは同じ物理メモリなので、入るモデルが小さくなる。T94 の第 3 段の宿題。
- 作るもの: GPU で動かす端末では、変換の `sink` から GPU のバッファへ直接書く。CPU に戻るときの扱い（読み直すか、両方持つか）を決める。
- **T152 からの申し送り（6 ビットの生成）**: T152 の生成は 1 ステップごとに層の重みを全部読むので、GPU に置いた広げた int8（int6 の 1.29 倍: 1.125 対 0.875 B / 重み）を読む。重みを 1 つにする T156 では 6 ビットを選ぶ理由（メモリ）も GPU の上で失う。**計測の道**: `/benchmark/` の層の表（T150・T175）に「int6 を行列の読みで広げる」融合した形の行を足し、広げた int8 の行と交互に測る（同じ `WIDEN_SIX` の SWAR を `fusedMatVec` の `block_dot` の読みに入れる形。元ネタが無いので Fable high）。覆す条件: 持ち主の端末でその行が広げた int8 の行より速ければ、エンジンの 6 ビットのモデルは GPU にも int6 で置く。
