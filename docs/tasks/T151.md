- **取った元ネタと理由**（`.tmp/t150-review/mlc/` の llama.cpp 95887577・MLC LLM 9fa644f5・TVM e0ed4aad・WebLLM の `llm_chat.ts`）: 罰は MLC の `apply_penalty_inplace`（1 スレッド 1 トークン）に CPU の規則（最近の 64、同じトークンは 1 回、正なら割る・負なら掛ける。MLC の出現回数の罰はエンジンに無い）。最大とその最初の index・softmax は llama.cpp の WebGPU の `argmax.wgsl`（対をワークグループのメモリで畳む。同じ値は小さい index: NumPy の argmax と `ARGMAX` と同じ。llama.cpp は大きい index）と `soft_max.wgsl`（exp(値 − 最大)、木の和）に `kernel.ts` の温度と nucleus の床（最良の 1e-7 未満は exp の前に外す）。**top-p はソートせず MLC の `top_p_pivot`**（top-p を保つと分かった境と保たない境の間に pivot を置き、各 pivot 以上の確率の和を 1 回の読みで足し、境を pivot に動かす）。変えた所: pivot を float の値でなくビットで刻む（正の float はビットの順に並ぶ）ので、MLC の 1e-7 の幅でなく境の確率そのものに着く。読むのは床の上に集めたものだけ（MLC は毎回語彙全部）。**引き**: CPU はソートした nucleus を確率の高い順に歩き、乱数 × 質量を超えた所で止まる（WebLLM の `sample_with_top_p` も GPU の argsort の後に同じ: TVM の `sample_top_p_top_k_from_sorted_prob`）。SAMPLE は同じ pivot で「その確率以上の質量が乱数 × 質量を超える最大の確率」を探す: CPU の歩きが止まるトークンそのもの（同じ確率のものは index の順。CPU の quicksort の順は決まっていないので、どちらもその分布）。nucleus なしでは CPU は index の順に歩くので、llama.cpp の `cumsum.wgsl`（1 スレッドに連続した区間、区間の和をワークグループのメモリでスキャン）で最初に越えたトークン。床の上の集めも `cumsum.wgsl` のスキャン（数を足して index の順に詰める）。埋め込みの行は llama.cpp の `get_rows.wgsl`（Q8_0 の `copy_elements`: 重み × ブロックのスケール）。**なぜこの組か**: 同じ乱数で CPU と同じトークン（試験が数字で言える）。WebLLM の形（GPU で argsort）は語彙 128256 のソートが重く、MLC の serve の形（top-p の後は index の順に引く `multinomial_from_uniform`）は分布は同じでもトークンが CPU と合わない。写した行の上に llama.cpp の MIT の許諾文の全文と、MLC・TVM・WebLLM の Apache-2.0 の文。
- **元ネタの無い部分（持ち主の決まりで Fable high に回す候補）**: (1) トークンからトークンへの状態の運び（`State` の並び、止まった後は何も変えない、Step への写し）、(2) 引きを top-p の pivot の探しで行う形（MLC の探しを、ソートした歩きの止まる位置を探すのに使った）、(3) pivot を float のビットで刻む変え方、(4) 同じ確率のトークンを index の順に数えて選ぶ所（`cumsum` のスキャンで数える）、(5) 探しの境をスレッド 0 が決めて `workgroupUniformLoad` で配る所（ループに barrier があるので一様に）。
- **元ネタの無い部分は Fable high が確かめた（2026-09-27、同じブランチ）**: 5 つとも形は残し、直したのは (5) の書き方 1 つ（境の `bounds` と `bound_sum` を 1 つの構造体 `Bound` にして、ラウンドごとの `workgroupUniformLoad` を 2 → 1: barrier が 1 つ減り、書く所も 1 つ）と検査 3 つ。理由と数字:
  - (1) 状態: `State` を書くのは SAMPLE の `finish()`（t = 0 だけ、全部の読みの後の barrier の後）なので競合は無い。止まった後のパスは同じ token・同じ pos で同じ計算をして同じ K と V の行を書き直す（入力もディスパッチも同じ。その行は止まった後は使われない）ので「何も変えない」は成り立つ。**読み戻し**: `sampled` は止まりのトークンを数に入れる（`chosen[sampled − 1]` が止まり）、`stopped` = 1、`token`・`pos`・`history` は止まりの前のまま。N の途中で止まっても CPU は `chosen[読んだ数 .. sampled)` を読めばよく、余った乱数は捨てる。`sampled` は run の頭からの通し番号（`chosen` と `randoms` の添字）なので、T152 で submit ごとに読むなら `chosen` の読む位置を進めるか、submit の間に `sampled` を 0 に書き直して乱数を入れ直す（申し送り (e) に足した）。
  - (2) 引き: S(w) = Σ_{p ≥ w} p とする。CPU のソートした歩きが止まるトークン（確率 w*、k 番目）は c_k > goal ≥ c_{k−1}。S(w*) ≥ c_k > goal で通り、次に大きい確率 w' では S(w') ≤ c_{k−1} ≤ goal で通らないので、**w* は S(w) > goal の最大の w**。同じ確率の何番目かは ⌊(goal − S(w')) / w*⌋（`nth`）。厳密な算術でこれが成り立ち、違うのは丸めだけ（下）。
  - (3) ビット刻み: 正の float はビット順 = 値順で、S は存在する確率でしか変わらないので、通る最大のビット列は存在する確率そのもの（MLC の 1e-7 の幅の終わりの条件が要らない）。pivot をどこに置いても区間は正しく縮む（置き方が決めるのはラウンド数だけ。壊し方が無いのはそのため）ので、見たのは終わり方（`spacing ≥ 1`、`u ≤ hi − 1` で区間は毎ラウンド必ず縮む）とラウンド数: ⌈log4(hi − lo)⌉ で、nucleus の探しは bits 0 → 1.0 の 2^30 で 15 ラウンド、引きは nucleus の確率 → 1.0 で 10〜14（JS の模擬 `.tmp/t151/fable/rounds.mjs`。top-p 0.5 で nucleus が最上位 1 つなら引きは 2〜3）。
  - (4) 同じ確率: index 順の数え（scan の排他和 + 自分の塊の順）は正しい。CPU の kernel の quicksort は同じ確率の順が不定なので分布は同じ。**ただし nucleus の境に同じ確率が並ぶとき、GPU は S(w) ≥ limit の定義で同じ確率のトークンを全部 nucleus に入れ、CPU はソートで先に来たものだけ入れる（質量が違い、引きも違う）。** どちらも top-p の読みとして正しく、起きるのは float32 の logits が境でちょうど等しいときだけ（実物のモデルではまず無い。検査の `tiedLogits` は境に同じ確率を置かない）。
  - (5) uniformity: `bound` は t = 0 が書き、全員が `workgroupUniformLoad`（前後に barrier）で読むので、ループの条件が一様で中の `total4` の barrier が許される。subgroup の演算は使っていないので幅（4・16・32・64）に依らない。lavapipe の幅 4・16・32・64（`LP_NATIVE_VECTOR_WIDTH` 128・512・1024・2048）で通り、`bound` を素の読みにした写しは Dawn の uniformity の検査で断られる（「'workgroupBarrier' must only be called from uniform control flow」）。
  - **±1e-4 の許しは要る**: GPU と CPU の差の上限は exp の精度（Vulkan は 3 + 2|x| ULP、x ≥ −16.1 で 35 ULP ≈ 2.1e-6 の相対）と float32 の和の合わせた上限。和の最悪は 1 スレッド 501 個の逐次で 501 × 2^-24 ≈ 3.0e-5、exp と scan の木 8 段を足して約 3.3e-5 × 質量（ふつうの丸めは打ち消し合って約 3e-6）。CPU は float64 の和。**1e-4 は最悪の上限の約 3 倍**（レビュー、2026-09-27。前の記録の「30 倍」はふつうの丸めに対してで、上限に対してではなかった）で、境が 1 トークンの確率（普通 1e-3 以上）だけ動く誤りは捕まる。**ずれる場合**: (a) 乱数が境から 3.3e-5 × 質量の内（見たものは全部 nucleus なしで乱数が 1 の直前: 尾のトークンの累積が f32 の丸めで入れ替わる）、(b) 上の (4) の境の同じ確率、(c) 温度 0 は完全一致。
  - **語彙 128256 の SAMPLE の費用（式）**: 語彙 V、床の上（最良の 1e-7 倍以上）の数 C、ラウンド R_n ≈ 15・R_d ≈ 10〜14 として、読み = 3V（argmax・exp・集め）+ (5 + R_n + R_d) C の float32、barrier ≈ 60 + 9 (R_n + R_d) ≈ 300 強。模擬で spread 2・T 0.7 は C ≈ 4% で 4.3 V = 2.2 MB、**全部が床の上（T 1.3、または平らな logits）で 37 V = 19 MB**。1 つのワークグループの読みの速さは未計測なので、時間は端末の表「the sampling alone」で見る（模型の logits と、全部が床の上の平らな logits の 2 つ。床の上の数も出す）。Android の読み戻し 3〜8.6 ms と比べるのはその数字。**減らす手（端末で越えたら）**: ラウンドあたりの pivot を 3 → 7（vec4 の累算器 2 つ）で log4 → log8 になり、R_n + R_d は 29 → 19、床の上の読みが 2/3。nucleus の探しの lo を床の確率（exp(−16.118) のビット）から始めれば 15 → 14。多くのワークグループに分けるのはその後。
  - **CPU の kernel の穴（範囲外、持ち主の判断へ）**: `sample()` の llama2.c 流の足切り（(1 − top-p) / (n − 1) × total 未満は外す）は、最大の確率がそれより小さいとき（床の上の数 < 1 / top-p: 平らな分布で top-p が 1e-3 級）に全部を外して `index[−1]` を読む（llama2.c も同じ）。一覧の設定（0.9）では起きない。GPU は同じ確率を全部入れるので壊れない。

- **Dawn + lavapipe**（ほかの担当が走っていて load 5〜12）: 検査の節は幅 4 で全部 ok を 4 回、幅 16（`LP_NATIVE_VECTOR_WIDTH=512`）で全部 ok（検査 181 秒）。`sampling` で CPU の最初の選びと違って境で通ったトークンは 91（最初の履歴の形では 82）のうち 1〜6（見たものはどれも nucleus なしで乱数が 1 の直前: 尾のトークンの累積が float32 の丸め（質量の 6e-8）の内で、CPU の float64 の歩きと入れ替わる）。`tokens on the GPU` は 12 トークンとも CPU の最初の選び（境 0）。**SwiftShader**（Playwright の Chromium、load 7、`.tmp/t151/probe.mjs` で GPU の Worker の段を 1 つずつ）: `sampling` ok（91 トークン、境 4）、`tokens on the GPU` ok、それまでの検査も全部 ok、`generate` は小さいモデルで回った。**わざと壊すと落ちる**（`.tmp/t151/mutate.py`、lavapipe の幅 4 と 16）: 19 通りとも落ち、壊していない写しは両方で通った。top-p の境（質量を掛けない、境のトークンを外す、1 − top-p）、罰（向き、重なりも罰する、窓の半分だけ、短い履歴の空の枠も）、乱数（いつも最初、1 つ先）、止まり（見ない、止まった後も進む、止まりで位置を進める）、輪の枠、nucleus なしの引き（最後に越えたもの）、温度、argmax の同じ値（大きい index）、埋め込みの行、RoPE の表の行、引きを全体の質量の割合で。最初の履歴（最も確からしいトークンが窓の外）では「重なりも罰する」と「窓の半分だけ」が通ったので、窓の中に最も確からしい 3 つを 2 回ずつ、窓の前に 3・4 番目を置く形に作り直した。境の「>」と「≥」の入れ替え（引きの pivot）は等しい和のときだけ違うので壊し方にしなかった。
