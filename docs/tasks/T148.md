  1. **旗なしで GPU**: WebGPU のある Worker では、どのモデルでも GPU の Worker を作る。`?gpu=on` は外し、試験用の旗 `?gpuTest=on` を置いた（名前と理由: CI と開発機の WebGPU は SwiftShader だけで、ページはそれを断るので、ページの GPU の道を試すには許す旗が要る。`fallback`・`always`（GPU の方が遅くてもブロックを回す）・`quick`（形を 1 つ目の正しいもので測らずに決め、ブロックも測らない: SwiftShader で Llama 3.2 1B の形の計測が 180 秒の期限を越えた、T147 の本番の CI））。`tests/gpu-check.mjs` は `gpuForce` の `fallback`・`always` で。GPU を切る旗は作らなかった（試験の道具は要らない。旗なしの Playwright の Chromium はアダプタが無く CPU）。
  2. **GPU を待たない準備完了**: 準備完了は CPU の準備だけで出し、GPU の準備（転送・コンパイル・検査・計測）が終わったら `{type: "gpu"}` でステータス行を書き直す。GPU は次のブロックから（`gpuEnd` より先から始まるブロックは CPU）。

  4. **選び方**（`forward.js` の `promptTimes()`、`tests/gpu-choice-check.mjs`）: ブロック（64 トークンまで）ごとに、GPU の時間 =（`gpu.js` が準備の最後に測った 16 と 64 トークンのブロックの直線）×（本物のブロックの時間との比の中央値）と、CPU の時間 =（本物の 16 トークンのブロックの ms / トークンの中央値、その本数で）× トークン数を比べ、GPU が 0.95 倍より速ければ GPU。**揺れ**: どちらも中央値（直近 5 つ）、GPU の 2 つの大きさは交互に 3 回ずつ（温めの 1 回ずつの後）、CPU は 2 つ集まるまで決めない（休んだ後の最初のブロックが遅く、1 つだと GPU に傾く）、GPU の準備中の CPU は数えない。**熱**: 8 回の生成ごとに 1 回（スレッドの見直しと 4 回ずらす）選ばなかった側で測り直し、GPU の比は本物のブロックごとに更新。**短いプロンプト**: ブロックが小さいと GPU の固定費が勝つので CPU（しきい値は計測から決まり、ステータス行に出る）。GPU の準備ができた後も、CPU の 16 トークンのブロックが 2 つ集まるまでのプロンプトは CPU（CPU の時間が要るので。計測だけの仕事はしない形を取った。1 つのプロンプトは「GPU のブロック、そのあと CPU」の順にしかならないので、CPU で測り始めたプロンプトの残りを GPU に回すことはできない）。**n と 2n の差は使っていない**: 比べたいのは submit の待ちも読み戻しも入った「ブロック 1 つの実時間」なので、待ちを消す形は合わない。

  8. `?bench=1` のラウンドは GPU を作らない。スレッドの検索は GPU の準備中は止める。
