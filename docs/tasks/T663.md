### T663 [バグ][解析分割] Qwen3 0.6B で 4 文・Pythia 70M で 6 文、本物の tokenizers と読みが違う — 状態: 完了（レビュー済み 2026-11-21）。前の状態: 反映済み（2026-11-13、T509 のレビューから。規模 小。T509 より前から同じ数）
- **原因**（2026-11-21、Opus medium）: 前分割（`CharClasses`・`STAGES`・`merged()`）ではなく **正規化**。本物の tokenizers（0.23.3）の NFC・NFKC は Unicode 9.0 の表（`unicode-normalization-alignments`）で、Python（.venv も Pyodide 314.0.7 も 3.14・Unicode 16）の `unicodedata.normalize` と、9.0 より後の字で違う: (1) 後から結合クラスが付いた 120 の印（U+089B・U+1AC3・U+1715・U+0C3C など）を本物は並べ替えない（10 文は全部これ: 例 `"\u089b\u17d2"` を Python は U+17D2（クラス 9）を前に出す）、(2) 互換の分解 170 字（U+32FF ㋿ を Python の NFKC は「令和」に、本物はそのまま）、(3) 合成 21（U+11935 U+11930 → U+11938 など、Unicode 13・16 の字）。全符号位置を本物の `NFC()`・`NFKC()` と比べて数えた。
- **直し**: `engine/tokenizer.py` に表 `UNNORMALIZED`（323 字、67 の範囲）と `normalized_as_read(text, form)`: 表の字で文を切り、間だけを Python で正規化して表の字はそのまま残す（本物にとって表の字は分解も合成もしない始まりの字なので、切っても同じ）。`Tokenizer.normalized()` の nfkc・nfc がこれを呼ぶ。エンジンだけで、変換器の出すもの（tokenizer.bin・options）は変わらない: **`CONVERTER` は上げない**。
- **確かめ**: 全符号位置 × 3 つの置き方（1 字・印の間・印の前）と、正規化に関わる 19,334 字から引いた 30 万文を NFC・NFKC とも本物と比べて違い 0。`tokenizer_json_check.py` は Qwen3 0.6B 4 → 0 wrong、Pythia 70M 6 → 0 wrong（`--planes 17` で 2,333,382 文・2,333,381 文とも 0）。試験は `test_tokenizer.py` の `test_the_normalizers_are_the_tokenizers_librarys`（軽い組、本物なしの 7 つの文）と `test_every_code_point_is_normalized_as_the_tokenizers_library_does`（`EVERY_CODE_POINT=1`、本物と全符号位置）: 壊し方（表から U+1ABF〜U+1ACE を外す）で 4 つとも落ちる。pytest 4,414 passed、smoke ok（Pyodide 314.0.7）。
- **送る ID が変わる所**（取りまとめ役の決め: 稀な字だけで本物に合わせる向き。AGENTS.md の 2026-10-10 の規則）: NFC か NFKC を言う tokenizer.json の項目（Qwen 系の全部・Pythia の 5 段・GPT-NeoX の系など。GGUF だけの変換の `GGUF_NFC` も同じ関数）で、文に表の 323 字が書かれたときだけ。例: Qwen3 で `"\u089b\u17d2"` は前 [44258, 240, 156, 95, 249] → 後 [156, 95, 249, 44258, 240]。NFKC の項目では「㋿」が「令和」の ID でなく ㋿ のバイトになる。書式の 9 つの問いと変換器の出力は変わらないので `conversions_compare.py` は回していない（何も変わらないことが式で分かる）。CI は省いた。訳: エンジンの Python だけで、pytest・smoke・本物との全符号位置の比べが手元で踏む。
- レビュー（Sonnet high、2026-11-21）: **直しを 3 つ入れて OK**。(1) 全符号位置の試験が `suite.sh full` のどの行にも無く毎晩も回っていなかった（コメントは「full が回す」と言っていた: 行は `test_bytebpe.py -k every_character` だけ）ので 1 行足した（約 10 秒）。(2) 全符号位置の試験は第 1 半の字（U+11935: 隣に U+11930 が要る）を見られず、表から外しても通った: 各字の NFD・NFKD も置き方に足し、外すと U+11938 を名指して落ちる（置き方は 5 つに）。(3) `normalized_as_read()` は ASCII の 4,000 字で 476 µs（`unicodedata.normalize` は 0.1 µs、tiny の BPE の encode で +20%）: `unicodedata.is_normalized` で正規化済みの文は切らずに返す（日本語 4,400 字で 13 µs、1M 字 3.9 ms）。**確かめて問題なし**: (a) 「切っても同じ」の読みは、表の字は本物にとって ccc 0 の始まりで、並べ替えも合成も隣の字と境をまたがない（9.0 の分解・合成の表に表の字が無いため）。別に 800,000 の文（表の字・古い印・古い合成の相手の始まりの字・Hangul・互換の分解を持つ字から 1〜7 字）と、全符号位置の NFD・NFKD の対と前後に印を置いた形（NFC・NFKC とも）を本物と比べて違い 0（置き方の力は、表から 1 つ外すと違いが出ることで確認）。(b) Pyodide 314.0.7 の Python は 3.14.2・Unicode 16.0.0 で .venv と同じ。(c) `GGUF_NFC` は「原本の tokenizer.json の言う NFC」を写す表なので、相手は tokenizers でよい（llama.cpp の NFD の表ではない）。(d) charsmap の道（`charsmap.replaced()`）は触っていない。(e) 変わる ID の項目: NFC を言う tokenizer.json は 73 項目以上（Qwen3・Qwen3.5・Bonsai・Pythia の 8 項目（14m〜6.9b）・DeepSeek-R1 Qwen 系・Qwen2.5 Coder・Swallow・Saluki・calm2 など。Qwen2.5 の Instruct 系 13 項目は取得が間に合わず未走査）、NFKC は `hf-gpt-neox-japanese-1.4b` と `hf-tanuki-8b-dpo-v1.0` の 2 項目（㋿ が当たるのはこの 2 つだけ）。**残る危険（直していない）**: 表は Python の Unicode 16.0.0 との差なので、**Pyodide を最新に追う方針（方針 2）のまま Pyodide が Python 3.15（Unicode 17）に上がると、Unicode 17 の新しい字は黙って本物と違う読みになる**（全符号位置の試験は CI の 3.14 に留めてあるので名指さない: T630）。出る差は新しい字だけで、deploy を止めるほどではない。毎晩の smoke に `unicodedata.unidata_version` の警告を足す案（採番は取りまとめ役）。台帳の書き違い: 「Pythia の 5 段」は NFC の項目が 8 つ、確かめの「3 つの置き方」は今は 5 つ。
