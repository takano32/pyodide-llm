### T.155 [追加][WebGPU] 6 ビットの重みと 64 ビットのメモリ（大きいモデル）を GPU で — 状態: **完了（レビュー済み、本線に入れた ddeeafc）**
- 6 ビット（Safari の既定と、`deviceMemory` の小さい端末）はシェーダで広げる。64 ビットのメモリのモデルは、重みを GPU へ塊で送る（1 つのバッファの上限、T.94 の記録）。
- **形（つなぎ、Opus medium）**:
  1. **6 ビットは GPU に置くときに 1 回だけ int8 に広げる**（GPU には int8 だけを持つ）。6 ビットの値は「下 2 ビットが 0 の int8」でスケールは 4 分の 1（T.98）なので、広げた値とチェックポイントのスケールはそのまま int8 の行列で、積はビット単位で同じ。だからタイルの行列積・形の検査・計測・線はどれも今のまま。行列積の中で広げる形（Q6_K の llama.cpp のように）は、形ごとに 5 つのシェーダを書き換えることになり、読みは 6.5/8 に減るが速さは未計測: 採らない（覆す条件: 持ち主の端末で 6 ビットのモデルのプロンプトが帯域律速と出て、int8 の読みが時間の大半のとき）。GPU の上の大きさは int8 と同じ（`gpuUnfit` の見積もりは前から int8 で数えていた）。
  2. **広げのシェーダは元ネタが無い**（llama.cpp の Q6_K は詰め方が違う）ので **Fable high の担当**。`shaders.js` の `WIDEN_SIX` は `null` のまま置き、口の仕様をその上のコメントに書いた（下）。`null` の間は GPU の Worker が「int6 weights are not on the GPU yet (the shader that widens them is to be written)」で CPU に戻す（(7) で入った後、この門はレビューで外した）。JavaScript の答え `sixValues()`（`llama2_numpy.unpack6` と forward.js の `weightAt` と同じ読み）と、読み込みの時の検査 `checkWiden()`（1000 グループの乱数のバイト（どの 24 バイトもグループになる）を幅 7 の行で 2 次元に配り、ビット単位で比べる。最後のグループの後の 64 グループぶんに書いていないことも）は書いた。
  3. **口の仕様**: `@group(0) @binding(0) var<storage, read> packed: array<u32>`（`pack6` のグループが 24 バイト（6 語）ずつ語 0 から。行列の塊ごとに別のバッファに上げ直す）、`@binding(1) var<storage, read_write> values: array<u32>`（同じグループを 32 個の int8（8 語）ずつ、グループの値 j はそのバイト j、1 語に 4 つで下のバイトが先）、`@binding(2) var<uniform> widen: vec4<u32>`（x がグループの数）。`@workgroup_size(64)`（`WIDEN_SIX_WORKGROUP`）、1 スレッドが 1 グループ、グループの番号は (workgroup_id.y × num_workgroups.x + workgroup_id.x) × 64 + local_invocation_index で、widen.x 以上のスレッドは何もしない。ディスパッチは `sixDispatch(groups, maxComputeWorkgroupsPerDimension)`（1 次元の上限を越えたら y へ）。
  4. **64 ビットのメモリ**: gpu.js は番地を Number（2^53 まで正確）で受け取り、型付き配列の区間の view と `writeBuffer` の写しで読むので、形は 32 ビットと同じ。変えたのは `block()` の行と角の読みを、メモリ全体の `Float32Array` から要る区間の view にしたところだけ（数 GB のメモリの全体の view をブロックごとに作らない）。`forward.js` の「a 64-bit memory: not on the GPU yet」を外した。
  5. **1 つのバッファの上限を越える行列は行の塊に**（`piecesOf()`）: 塊は行まるごと、バイトは `min(maxStorageBufferBindingSize, maxBufferSize)` 以下、塊の最初の行は出力を束ねられる所（`minStorageBufferOffsetAlignment` / 4 の倍数: 既定の 256 なら 64 行）。塊ごとに値とスケールのバッファ、束ね（出力は塊の最初の行から `{ buffer, offset, size }` で束ね、トークンの行の幅 yStride は行列全体の行）とディスパッチ。**元ネタ**: llama.cpp の WebGPU は 1 つのテンソルを 1 つのバッファに入れ、上限は `maxStorageBufferBindingSize`（`ggml_backend_webgpu_buffer_type_get_max_size`: 「maxBufferSize might be larger, but you can't bind more than maxStorageBufferBindingSize」）で、越えるテンソルは断る（commit 2145525a、MIT、写した行は無い）。うちは T.94 の設計（分類器が上限を越えるなら行の塊に）どおり断らずに刻む。**一覧のモデルの層の行列はどれも WebGPU の最小の上限 128 MiB に入る**（最大は Qwen2.5 7B の w1 の 68 MB、Llama 3.1 Swallow 8B の w1 59 MB）ので、今の一覧で塊に分かれる行列は無い（試験は `pieceBytes` で小さく刻ませて見る）。
