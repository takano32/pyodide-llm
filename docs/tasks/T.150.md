### T.150 [性能][WebGPU] 融合でディスパッチを減らす — 状態: **完了（レビュー済み、本線に入れた 04ce68d）**
- 根拠: 1 トークンに約 240 回のディスパッチで、空のディスパッチだけで 2〜9 ms（持ち主の Android）。ベンチの「fused」は回数の効きだけを見る形で、計算の中身は畳んでいない。
- 作るもの: 同じ入力を読む行列を 1 つに（q・k・v、gate・up）、norm を次の行列の入力の読みへ、残差の足しを前の行列へ、本当に畳む。
- 完了条件（レビューの後、持ち主が「オススメで」と決めた）: 層あたり 5 回（行列 4 + attention 1）、Llama 3.2 1B の 1 トークンで約 226 → 約 82 回（0.36 倍）。持ち主の端末の層の表で、融合した形が交互に測った分けた形より、9 回ぶんの空のディスパッチ（「besides the weights」の表の 240 回の値 × 9 / 240）の半分以上速い。submit の待ちと読み戻しは T.151。
- 元ネタ: WebLLM / MLC の融合したカーネル（Apache-2.0）と llama.cpp の WebGPU の融合（`rms_norm` と掛け算、MIT）。
- **作ったもの（2026-09-27）**: `shaders.js` の `fusedMatVec({ input, output, subgroups })`（T.152 がそのまま使う 1 トークンの層の形）。1 層が 14 ディスパッチ（norm・q・k・v・RoPE とキャッシュ・attention・o・残差の足し・norm・gate・up・SwiGLU・down・足し）から **5**: ① q・k・v を 1 つの行列（行を続けて 1 つのバッファ）で、norm を入力の読みに、RoPE とキャッシュへの書き込みを書き出しに、② attention（プロンプトの flashTile のまま）、③ o と残差の足し、④ gate と up を 1 つのワークグループで、norm を読みに、SwiGLU を書き出しに、⑤ down と残差の足し。**頼みの「層あたり 3〜4」には届かない**: attention は全部の head の q・k・v が揃ってから（q・k・v の行列とは別のディスパッチ）、o は全部の head の出力が揃ってから（attention とも別）でないと始められず、WGSL にはディスパッチの中で全部のワークグループを待つ手段も float の atomic も無い（CAS の `atomicCompareExchangeWeak` で float の足しを真似ることはできるが、足す順が毎回変わってビットで再現せず、o の 1 つの行を 32 の head が取り合う）。行列 4 つと attention 1 つの 5 がこの形の下限（レビューの数え: WebLLM は層あたり 10、llama.cpp は約 17）。
- **取った元ネタと理由**（`.tmp/t150/ref/` に llama.cpp の `mmvq.cu`・`ggml-cuda.cu`、commit 2145525a）: 行列 × ベクトルは T.149 の llama.cpp の `mul_mat_vec`（広げる形、ワークグループの和か subgroupAdd）。**gate と up と SwiGLU は llama.cpp の CUDA の `mul_mat_vec_q` の融合**（`vgate` を `vx` と並べて同じ y と掛け、`tmp_gate` を同じように足し上げ、行を書くところで `result *= silu(gate)`）。頼みの「SwiGLU を down の読みへ」より、こちらを取った: 公開の形であることと、silu を要素に 1 回で済む（down の読みに置くと down のワークグループごとに hidden 個: 1B で 512 × 8192 回）。**残差の足しは同じカーネルの `x_bias`**（MUL_MAT の後の ADD を書き出しで `result += x_bias`）と MLC LLM の matmul + add の融合（`FuseDequantizeMatmulEwise`、Apache-2.0）。**q・k・v と gate・up を 1 つの行列**は MLC LLM の Llama の `qkv_proj`・`gate_up_proj`。**RoPE とキャッシュ**は llama.cpp の CUDA の rope + set_rows の融合（`rope_set_rows_ops`）を、行列の書き出しにまで寄せた（ワークグループの 4 行は RoPE の対とキャッシュの float16 の対を丸ごと持つので書ける。回し方は `ROPE` と同じ式）。**norm を読みへ**は公開の WGSL が無い（llama.cpp の WebGPU は norm と重みの掛け算だけを畳む、`rms_norm_mul.wgsl`）: norm の尺度は行全体で 1 つの数なので行列の外に出せ（W·(g ⊙ x·s) = s × W·(g ⊙ x)、FlashNorm、arXiv 2407.09577 の「尺度を行列の後へ」）、ワークグループはどのみち x を全部 1 回読むので、x² の和を行の和と同じ足し上げに 1 つ足した。この数行はこのプロジェクトのもの（式は `rms_norm_mul` と同じ）で、レビューで見てほしい所。写した行の上に llama.cpp の著作権の行と MIT の許諾文。
- **ベンチ**（`/benchmark/` の GPU の節、`{ step: "layer" }`）: Llama 3.2 1B の幅の 1 層（位置 127: attention は 128 位置）を 3 つの形で: 分けた形（RMSNORM・T.149 の `mulMatVec`・ROPE・flashTile・SMALL・SWIGLU、14 ディスパッチ）、norm だけ別のディスパッチにした融合（`fusedMatVec` の input "plain"、7。norm を読みに畳む効きを切り分ける、レビューの should 3）、融合（5）。どれもワークグループの和と、subgroups（と `subgroup_id`）のある端末では subgroupAdd でも。全部の形が同じ重み（層の 4 つの行列）を読み、分けた形は行の範囲をバインドする。**測り方（レビューの must-fix 1）**: 形ごとに n（1 つの submit の層の数、層ごとに次の重みのコピー、合わせて 128 MiB 以上: 1B の層は 68.4 MB なので 2 つ）を 40 ms まで倍々に決め、そのあと n と 2n の組を**形を交互に** 5 巡（T.147 の `timeForms` の形、`interleaved()`）。組の比の中央値が 1.6〜2.2 を外れた形があれば 5 巡を 1 回取り直し、なお外れたら unsteady。それまでは形ごとに `paired()` を続けて測っていたので、端末が温まって遅くなると後の形が損をした。フォールバックのアダプタでは 1 回ずつ、コピー 1 つ。表（`src/bench.js` の `layerTable()`）は「dispatches・GPU ms・GB/s（層の重み ÷ 時間。括弧に T.168 のバッファの読みに対する %、レビューの should 2）・16 層ぶんの ms・分けた形の何倍速いか」で、何倍かは同じ和の形の分けた形に対して。何倍かは失ったデバイス・フォールバック・WRONG・unsteady では出さず、% は失ったデバイス・フォールバック・読みの上限が unsteady では出さない。T.134 の「fused」「fused and chosen on the GPU」の行（回数の効きだけを見る代わりの形）は外した。
