- **結果（2026-10-30）**: 案の「ブロックを `NOT_FINITE` で止める」を、Python の止まりに乗せる形にした（取りまとめ役の決め: 止める道を新しく作らない）。(1) カーネル `to_f16` は、渡された float32 のうち NaN と無限大の数を返す（`exponent >= 31` の枝の中で指数が 143 のときだけ数える: 普通の道に命令を足さない。大きすぎる有限の数（70000 など）は今までどおり無限大に書き、数えない: float32 のキャッシュでも有限のまま）。(2) `forward/cache.ts` は、そういう値を書いた最初の位置を持つ（`put()` に位置の引数、`unfiniteBy(pos)`）。位置 pos 以前から書き直すと消える（`written(pos)`: CPU の `run()` と GPU の書き戻し `fromStaging()` の頭）。(3) `run()` は、logits を作るトークンがその位置以降なら logits を全部 NaN にする: float32 のキャッシュなら NaN が広がって logits も有限でなくなる所で、同じく Python の `NOT_FINITE`（T.195）で止まる。(4) GPU の答えのステップは CPU のキャッシュをそこから上げるので、その位置以降のステップは GPU に頼まず CPU に回す（`gpuside.ts` の `generateMany()`: CPU のステップの logits で止まる）。新しい検査 `tests/unfinite-check.mjs`（軽い組: カーネルの数え、本物のカーネルの上のエンジンで NaN を 1 つ入れた位置から後が NaN・書き直しで戻る・プロンプトのブロック・float32 のキャッシュは何もしない）、`gpu-part-check` に GPU のステップを断る場合、`kernels-in-browser.mjs` に `to_f16` の数えと半精度のビット。壊し方 5 つ（logits を NaN にしない・`run()` の `written` を外す・位置を 1 ずらす・カーネルが指数 142 を数える・GPU の門を外す）はどれも落ちた。GPU の書き戻しの `written` は試験が踏まない（書き戻しの値は T.243 が有限と確かめた後）。

- **残る違い（取りまとめ役の読み）**: 窓のある層だけのモデルでは、NaN の位置が窓を外れた後も logits は NaN のまま（float32 のキャッシュなら窓の外では読まれない）。実際は NaN の位置のトークンの残差が NaN になり、窓の中の後のトークンにも広がるので、止まる所はほぼ同じ。窓のある層だけのモデルは一覧に無い（Gemma 3・Spark は全部を見る層も持つ）。
- CPU の `to_f16` は NaN を無限大として書き、読み（`halves4`・`half`）は無限大を ±65536 に広げる。float16 のキャッシュ（共有メモリで GQA でないモデル、T.110・T.160）では、プロンプトの途中のトークンで出た NaN が後のトークンから見えない（最後のトークンの logits が有限なら T.195 も通る）。案: `to_f16` の書きの所で有限でない値を数えて、そのブロックを `NOT_FINITE` で止める。attention の内側のループには触らない。
