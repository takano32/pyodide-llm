- 根拠: 「A prompt」の GFLOPS が端末の上限の何 % かを出せない（T.163 の GPU 版）。T.146 のレビューの見積もり（Android の Immortalis-G715 MC11 の FP32 は仕様から 1.4〜3.2 TFLOPS、未計測）では、今の `BATCHED` は 1.4〜3%、llama.cpp の 32×32 は共有メモリの読みで律速されて 5 倍に届かない見込み、DP4A は届く見込み。どちらも実測の上限が無いと確かめられない。

- **元ネタ**: clpeak（https://github.com/krrishnarraj/clpeak、commit 3a3547105933、`src/opencl/kernels/` の `compute_sp`・`compute_int8_dp`・`global_bandwidth` と `mad_chain.cl` の注記）。**GPL-3.0 なので行は写さず、形（ループの作り方）だけを取って WGSL で書き直した**（このリポジトリに GPL の行を入れない。`shaders.js` のコメントに出どころとその旨）。取った形: 積和は 2 乗の漸化式 x = x·x + c（c はレーンごと、ループの外で決まる。代数で畳めない）を vec4 の 2 本（1 スレッドに独立な 8 本。clpeak の「幅 4 からは 1 本」）、dot4I8Packed は 2 つの累算器が互いを読む鎖 a = dot(x, b) + a、b = dot(x, a) + b を 4 対（clpeak の compute_int8_dp: 両方の入力がループで変わらないと、コンパイラが掛け算 1 つに畳める）、グローバルの読みは clpeak の `global_offset`（各読みがディスパッチのスレッド数だけ離れ、隣のスレッドが隣の vec4 を読む。バッファを 1 ディスパッチで 1 回）。共有メモリは clpeak の形（書いて barrier して隣を読む往復）を取らず、読みだけのループ（16 KiB を 1 回埋め、ループで動く番地から vec4 を 16 回）にした: 頼みが「読みだけ」で、clpeak の形は barrier の速さも測るため。gpuinfo.org は機能と上限の一覧で計測の形は無い。Chips and Cheese の道具は見ていない（clpeak の形で足りた）。**c は [-1.55, -1]**（実軸のマンデルブロ集合の中: 値は [-2, 2] に留まり、無限大や非正規数の速さを測らない）。
- **測り方（レビューの後）**: まずループの回数（`plan.loops`、4 から倍々）を 1 ディスパッチが 2 ms を超えるまで伸ばし（8 ディスパッチの submit ÷ 8 で見る。ディスパッチごとの費用を小さくする）、次に 1 つの submit のディスパッチの数 n を 40 ms を超えるまで伸ばす。**n 回と 2n 回を交互に 5 組**測り、組ごとの差の中央値を n 回ぶんの時間にする（submit の固定費は両方に入って消える。持ち主の Android で待つ submit 1 回 3.7 ms、T.134）。組の 2n ÷ n の中央値が 1.6〜2.2 を外れたら 5 組を測り直し、それでも外れたら「unsteady」と書いてプロンプトの割合に使わない。全部を validation と out-of-memory のエラースコープの中で走らせ、端末が断ったパイプライン・バインドグループ・バッファは数字でなく誤りにする。ループの回数が 16384 まで伸びても 2 ms に届かないか、n が 4096 まで伸びても 40 ms に届かなければ、ループが仕事をしていないとして誤り。**積和は 2 つの形**を測って速いほうを上限にする: 2 乗の形（vec4 の 2 本）と、clpeak の affine の形 x = x·a + b（vec4 の 1 本、a と b は uniform から来る一様な係数 0.999 と 0.001。3 つの入力が別のレジスタ: Intel の GPU は同じレジスタを 2 回読む積和を半分の速さにする）。グローバルの読みは 128 MiB（WebGPU の既定の binding の上限。端末の上限が小さければそれに合わせる）。フォールバックのアダプタでも同じ大きさで走る（最初のループの回数 4 から伸ばすので、SwiftShader でも 1 つの上限が数秒〜数十秒）。測る順は「A prompt」の直前（同じくらい温まった端末で比べる）。
- **表**: 「The device's ceilings」（f32 と f16 の積和 GFLOPS と速かった形、int8 dots GOPS、ワークグループのメモリ（16-byte reads）と 128 MiB のバッファの読み GB/s。f16 は shader-f16 のある端末だけ、int8 は packed int8 dot のある端末だけ）。「A prompt」の表の「of the ceiling」の列は、packed の形は int8 dots、**ほかは全部 f32 の上限**（llama.cpp の f16 のタイルは共有メモリに f16 で置き、f32 で掛けて足す: 元ネタの `mul_mat_reg_tile.wgsl` の `acc` が f32。レビューの must-fix）と、**バッファの読み × 2T ÷ 1.125**（int8 の重みとスケールの分け前が 1.125 バイトで、T トークンに 2T FLOP）の低いほうに対する割合。100% を超えた行には「past it: the ceiling read low」。フォールバックのアダプタでは割合を出さない。行列 × ベクトルの表の下に「最速がバッファの読みの何 %」の 1 行（フォールバックでは出さない）。
