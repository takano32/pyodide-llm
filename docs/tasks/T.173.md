### T.173 [調査・性能][その他] メモリを言わない端末（iPhone の Safari）で、どこまで載せるかを決める — 状態: **案 (1) は本線に入れた（73da2e1、レビュー済み）。持ち主の iPhone と Android の Page memory の数字待ち。(2)(3) は未着手**
- **根拠**: T.148 は GPU に重みを 2 重に持つモデルを「チェックポイント + `footprint()` + GPU の層が `deviceMemory` の半分を越えたら CPU」で決めるが、Safari は `navigator.deviceMemory` を持たないので 4 GB と見ている。この見方では iPhone の Llama 3.2 1B 以上はいつも CPU（見積もりの合計 2.86 GB、`.tmp/t148-review/room.mjs`）。6 ビットの判定（T.98）も同じ `deviceMemory` に頼っている。
- **いまの知見（2026-09-27、公開の資料から。持ち主の端末では未計測）**:
  - **User-Agent では決められない**: iOS の Safari は UA を固定していて、機種も OS の細かい版も出さない（どの iPhone も同じ形の UA）。
  - **WebGPU のアダプタの `maxBufferSize` は機種で変わる**（Metal の `maxBufferLength` を映す）: 公開の報告で iPhone 6 が 256 MB、iPhone 8 が 747 MB、iPhone 11 が 960 MB（gpuweb/gpuweb#1371）、最近の iPhone で約 1074 MB（microsoft/onnxruntime#26827、2025-12）。古い機種を見分ける目安にはなるが、新しい機種は同じ値に並び、RAM の量は分からない。
  - **効く上限は端末の RAM ではなく、1 ページが使える量**: iOS は 1 ページがおよそ 2〜3 GB（機種による）を越えると jetsam でタブを落とす（例外は出ない。だから「試しに確保して確かめる」は使えない）。iPhone 16 Pro Max の WebGPU で約 2.5 GB という報告（2025-07）、古い iPhone SE では約 100 MB で落ちたという報告（iOS 26.2、2026-01）もある。
  - **1B を GPU に置くと合計 2.86 GB + Pyodide で、この上限に近いか越える**。CPU だけなら約 1.8 GB。だから今の「4 GB と見る」は、1 ページの上限から見て結果として控えめで妥当（1B 以上は CPU、小さいモデルは GPU）。
  - `performance.memory` は Chromium だけ。画面の大きさと `devicePixelRatio` から機種の系統を当てる手は、Pro と無印で RAM が違うのに同じ画面の機種があり、決め手にならない。
- **作るもの（案）**: (1) 持ち主の iPhone で、`/benchmark/` に「このページがどこまで持てるか」を安全に測る段を足せるか調べる（jetsam は例外を出さないので、段階を小さく刻み、各段の前に `sessionStorage` に印を書き、落ちて読み直されたら前の段を上限とする形。文面は持ち主）。(2) `maxBufferSize` を古い iPhone で GPU を断る目安に足す。(3) 載せる線（今の 4 GB と見る）を、(1) の数字と T.156（重みを 2 重に持たない。入れば 1B の合計は約 1.8 GB）の後で見直す。
- **完了条件**: 持ち主の iPhone で、既定のページが落ちずに、載せられるモデルは GPU に載る線が数字つきで決まる。
